# Durable control-plane operations

## Scope and invariants

The initial durable slice owns two explicit finite state machines: service publication and invocation execution. PostgreSQL is authoritative for desired and observed state, state-machine version, generation, attempt, durable due time and deadline, lease owner and fencing token, error classification, terminal result, command idempotency, external-effect observation, event replay, outbox delivery state, command audit correlation, completed authentication attempts, completed API authorization decisions, and completed invocation Cedar decisions when the explicit durable evaluator is composed.

There is no generic workflow table or user-authored workflow language. The worker's polling ticker is only a wake-up mechanism; `due_at` remains the durable timer. Every claimed operation is selected fairly from the oldest due operation per isolation domain. A transition can commit only while the worker still owns the matching lease owner and fencing token.

The reference runtime stores provider-side receipts in `reference_runtime_receipts`. Invocation state-machine version 2 records distinct `start-invocation` and `run-invocation` effects, so successful sandbox admission cannot be mistaken for completed runtime work. Cancellation records a separate `cancel-invocation` effect and reaches its terminal state only after that deterministic effect is observed or applied successfully. The first accepted cancellation preserves the original requester while binding the cancellation actor and correlation as the principal for that effect; later cancellation attempts observe the request without replacing its authority. Existing version 1 operations retain their original single-effect reconciliation and effectless cancellation path without reinterpretation; only newly accepted invocations use version 2. Optional version 2 start and cancellation drivers resolve the invocation's persisted service, revision, current effect principal, and correlation scope. The runtime handoff is exposed only while the operation is running after a durably successful admission effect; it supplies persisted invocation input, the revision runtime profile and output schema, and current effect authority. A claimed handoff additionally requires the exact active lease owner and fencing token. The reconciler forwards the claim only to explicitly claim-bound effect routes; direct claimless calls, mismatched scope, and overlapping route ownership fail closed. Active workers may renew that lease without crossing the operation deadline. Before starting one native turn, a worker must consume a durable single-use runtime-attempt reservation under that same claim. Successful and terminal-failure completion are fenced, exact canonical replay is read-only, and conflicting terminal outcomes fail closed. A deterministic native failure terminates the operation with a bounded safe error; an unresolved reservation cannot be consumed again because the native session outcome is ambiguous. The optional runtime driver composes these boundaries with the exact admitted execution and Codex adapter: it requires a ready provider observation before reservation, authorizes the normalized profile-specific request immediately before provider access, starts one turn only after reservation, renews the same claim, and persists each normalized event before recording the terminal attempt. Its built-in `codex.app-server/v1` mapper accepts a bounded persisted `prompt` plus optional immutable artifact declarations, clones the persisted output schema, and fixes approvals to locked; declarations are bounded, uniquely identify clean absolute sandbox paths, and force workspace-write sandboxing before authorization, while requests without declarations remain read-only. Unsupported profiles and hidden native overrides fail before provider access. Successful turns materialize only acknowledged text deltas into a bounded declared result. Structured output schemas compile before provider access with a pinned default dialect and no external resource loading; the result must decode as exactly one conforming JSON value, while missing, malformed, non-conforming, or oversized output records a terminal runtime failure without repeating the native turn. An invocation-artifact finalizer provides bounded immutable-object creation, exact post-write observation, and deterministic private routing. After a successful native turn and valid declared output, the optional runtime driver exports declarations in their persisted order, derives stable isolation-scoped artifact identities, and finalizes sensitive content under a renewed exact claim before completing the attempt. Export or persistence uncertainty remains ambiguous and cannot repeat the native turn. Its PostgreSQL catalog requires the exact live version-2 runtime claim, runtime effect, and reserved attempt before atomically binding private object metadata, the existing public descriptor, and one bounded audit record. Exact committed replay no longer requires a live lease, so lost database acknowledgements remain observable without repeating the binding. The opt-in S3 object transport and OpenShell export-content boundary are available separately. Export uses an exclusively owned private workspace, accepts only a clean absolute sandbox path, bounds and verifies a single owner-only file, removes it before returning non-serializable bytes, and never exposes its host destination. Production/public driver composition and production artifact transport certification remain separate work. The opt-in governed composition owns all three version 2 routes together, keeps runtime claim-bound, and rejects any missing fallback, admission, runtime, or cancellation driver before a worker starts. Normalized adapter events require the same claim and recheck its live database lease at insertion while retaining a separate durable runtime-source sequence and one monotonic public invocation sequence, so stale workers cannot append, exact replay is read-only, and conflicting reuse fails closed. Admission observes any execution already created for the operation and requires explicit consequential-effect authorization immediately before new admission. Cancellation observes the exact persisted execution before any repeat, authorizes immediately before termination, treats an execution as safely absent only when admission was never prepared, and keeps a prepared-but-unresolved admission outcome retryable. A durable denial, structurally invalid target, or immutable execution-plan, enforcement-bundle, policy, or provider-state conflict records a bounded terminal failure instead of retrying. Missing admission prerequisites and policy-service, storage, gateway-capacity, and provider availability failures retain the bounded retry path. Reference mode routes all three effects to the deterministic reference driver. The explicit `governed-development` mode owns all three version 2 effects together for one configured isolation domain and keeps publication plus version 1 behavior on the reference driver. PostgreSQL can retain one audited, append-only invocation Cedar policy for each exact service revision and expose it through the same fail-closed policy-source contract used by static composition. An explicit audited authorizer can also withhold each completed effect-time Cedar outcome until PostgreSQL records its actor, complete durable scope, phase, correlation, policy-set identity, and exact digest. Installation is an explicit database-authorized operator action; governed development composition consumes only that exact installed record. The OpenShell adapter can persist protected gateway, placement, sandbox-routing, and observed-state records through its PostgreSQL state store; it is not a configured public execution path or a real harness certification.

## Migration policy

Run migrations as a separate deployment step before starting a new API or worker:

```shell
DATAGROUND_DATABASE_URL="$DATABASE_URL" go run ./cmd/dataground-migrate up
DATAGROUND_DATABASE_URL="$DATABASE_URL" go run ./cmd/dataground-migrate check
```

The migration runner takes a transaction-scoped PostgreSQL advisory lock, applies each embedded migration atomically, and records its version. API and worker processes require the exact current schema version and fail closed on an older or newer version. This deliberately disallows a mixed-schema fleet until a future migration explicitly declares a tested compatibility window.

For the current pre-production schema, the tested rollback is:

```shell
DATAGROUND_DATABASE_URL="$DATABASE_URL" go run ./cmd/dataground-migrate down-to-0
```

`down-to-0` deletes all control-plane data and is only for disposable development databases. Production migrations must add backup, expand/contract, and data-preserving rollback evidence before this command can be certified there. The CI migration test runs up, down, up, and exact-version validation against PostgreSQL 18.4.

## Deployment and recovery

1. Stop new command admission or keep the old API fleet running.
2. Back up PostgreSQL using the installation's verified backup procedure.
3. Run `dataground-migrate up`, followed by `check`.
4. Start workers, then API instances. Readiness requires a live database connection.
5. Confirm that due operations are claimed and that stale leases expire naturally.

Killing an API after command commit cannot lose the command because the resource change, idempotency result, outbox event, and audit record share one transaction. Killing a worker after an external provider acknowledgement may leave the effect status unknown; the next worker observes the deterministic effect ID before applying it again. Expired or replaced leases cannot commit because every transition is fenced.

The same worker process runs a separately bounded outbox dispatcher. It fairly claims one event per isolation domain, publishes through a replaceable publisher interface, and uses a fenced lease before marking delivery. The current reference publisher acknowledges locally for conformance testing; durable signed webhook transport remains a later publisher implementation.

## Repair

Only a failed operation is repairable. The operator must supply an authenticated actor identity from the surrounding administrative channel, a reason, and a stable deduplication ID:

```shell
DATAGROUND_DATABASE_URL="$DATABASE_URL" go run ./cmd/dataground-repair \
  -kind invocation-execution \
  -isolation-domain iso_example00000000000000 \
  -operation op_example000000000000000 \
  -actor operator@example.invalid \
  -reason 'provider recovered after incident' \
  -deduplication-id incident-123-repair-1 \
  -deadline 30m
```

The new deadline is required because the failed operation's original deadline may already have expired. Repair preserves the original request actor and correlation while recording the authenticated repair actor and deduplication correlation as the principal for subsequent effect authorization, transition audit, and invocation admission. The command is repeatable: its actor-bound deduplication record, operation transition, outbox event, and audit record commit atomically. Reusing the deduplication ID with different content, a different actor, or a different deadline is rejected. The reason contributes to the immutable command digest; the audit record carries the actor, operation, outcome, and deduplication correlation without copying free text into telemetry. It does not repair cancelled or successful operations. The repair executable remains outside the HTTP authentication boundary, so access to it and its database credential is still the authorization boundary; do not expose it through the public API.

## Safe telemetry

Reconciler spans contain operation kind, stable operation ID, isolation-domain ID, and attempt number. Outbox and audit payloads contain resource identity, outcome, actor, operation, and correlation identifiers. Invocation inputs, outputs, event payloads, provider responses, credentials, and raw errors are not exported through telemetry or audit metadata.

## Known limits

- Reference mode still uses the deterministic driver. The explicit single-domain governed development mode configures the complete version 2 authorization, admission, runtime, artifact, and cancellation boundary against pinned loopback dependencies; production/public composition, workload-authenticated storage, provider provisioning, and live runtime certification remain unavailable.
- Outbox rows are written atomically but external webhook delivery is a later bounded state machine.
- The HTTP API has loopback-only development bearer identity and static Cedar action-authorization boundaries. Durable mode records completed authentication attempts and API action evaluations in separate append-only PostgreSQL tables before releasing their results, with one correlation shared across both; process-local mode has no durable audit. Production OIDC verification, public policy authoring and approval, signed distribution, entity loading, dynamic reload, audit transport, encryption, acknowledgement verification policy, access and retention policy, provider credential brokering, production object storage, and artifact content delivery are not implemented. Governed phases can use an immutable static or PostgreSQL policy source, canonical Cedar input, concrete evaluator, shared authorizer, and append-only decision recorder. Reference mode does not configure this boundary; the explicit governed development mode does so only for its exact single-domain profile. Audited internal commands export bounded frozen pages, seal them through an external-key boundary, prepare an exact envelope for deployment-owned delivery, and record an external acknowledgement digest through a controlled PostgreSQL transition; transport execution, production access policy, legal hold, and retention remain unimplemented.
- The exact-schema startup rule means rolling mixed-version upgrades are intentionally unavailable until an expand/contract migration is tested.
