# Audit export delivery receipts

The version 5 delivery acknowledgement boundary accepts only a canonical `dataground.audit-export-delivery-receipt/ed25519/v4` document signed by a key in an immutable `dataground.audit-export-recipient-trust/ed25519-x25519/v2` profile that is active through the [recipient trust registry](audit-export-recipient-trust.md) with unexpired proof from a configured recipient-proofing authority. The receipt binds the delivery contract and identifier, isolation domain, export kind and identifier, envelope and export digests, export trust profile and signing key, recipient and destination, exact [encrypted-package](audit-export-encryption.md) digest and X25519 key, database-authorized recipient trust generation, and recipient-reported acceptance time. PostgreSQL accepts it only after the same package has completed its bound [immutable development transport](audit-export-transport.md). The runtime requires UTC with no finer than microsecond precision; it records that external time separately from the database acknowledgement time and does not treat it as a trusted clock.

The recipient trust profile contains the exact recipient identifier, one to eight sorted Ed25519 acknowledgement keys, and one to eight sorted X25519 encryption keys. Historical profiles must remain available with their packages and receipts because both bind the complete canonical profile digest:

```json
{"contract":"dataground.audit-export-recipient-trust/ed25519-x25519/v2","recipientId":"archive.primary","signingKeys":[{"keyId":"archive_signing_key_01","publicKey":"REPLACE_WITH_UNPADDED_BASE64URL_ED25519_PUBLIC_KEY"}],"encryptionKeys":[{"keyId":"archive_encryption_key_01","publicKey":"REPLACE_WITH_UNPADDED_BASE64URL_X25519_PUBLIC_KEY"}]}
```

The receipt `contentSha256` is SHA-256 over the compact canonical `content` object. The signing input is the ASCII domain `DataGround audit export delivery receipt v3`, a newline, then one compact JSON object with fields in this exact order: `contract`, `content`, `contentSha256`, `recipientTrustProfileSha256`, and `keyId`, followed by one newline. The nested `content` fields use the order published in `contracts/schemas/audit-export-delivery-receipt-v3.schema.json`. Sign those exact bytes as raw Ed25519 input and place the unpadded base64url signature in the receipt's `signature` object.

Both the receipt and trust profile must be duplicate-free one-line canonical JSON files with one final newline, mode `0600`, beneath owner-only directories. The verifier rejects symlinks, path collisions, mutable parent directories, unknown fields, alternate digest encodings, unsorted or duplicate trust keys, cross-kind export identifiers, substituted delivery, package, key, or generation fields, sub-microsecond timestamps, and signatures from keys absent from the exact bound profile. The canonical schemas and fixtures are under `contracts/schemas` and `contracts/fixtures`. Historical receipt versions remain accepted only for exact replay of their matching historical delivery contract and do not gain encryption or newer authorization claims.

Verification authenticates which pinned recipient signing key approved the exact encrypted package and delivery binding. PostgreSQL separately proves that its paired encryption key and the signing key belonged to the same exact active generation under an unexpired signed identity and key-custody proof with no matching effective recorded revocation, and that the exact package was verified at the bound immutable development object before acknowledgement. Selecting and governing proofing and revocation authorities, retaining underlying evidence, acquiring external notices, authenticated production transport, recipient decryption and access, retention, legal hold, deletion, and independent clock policy remain deployment responsibilities.
