# Local OpenShell execution boundary

DataGround's first OpenShell development profile is pinned and internally consistent, but it is not a complete runtime or production certification. The profile establishes the Docker gateway topology, immutable OCI inputs, an upstream deny-all policy fixture, the internal `ExecutionProvider` port, and the Codex app-server JSONL-over-stdio transport. The internal Codex adapter has protocol-level conformance coverage for its initial lifecycle, event, interruption, and approval surface. Provider-secret non-exposure is certified only for this exact pinned development profile by the incorporated coverage-qualified v3 record.

The machine-readable profile is [`deploy/openshell/development-profile.json`](../../deploy/openshell/development-profile.json), and its accepted record is [`deploy/openshell/evidence/openshell-credential-non-exposure-v3.json`](../../deploy/openshell/evidence/openshell-credential-non-exposure-v3.json). `pnpm openshell:profile:check` verifies the immutable image references, loopback topology, deny-all fixture hash, production-blocked state, runtime transport, accepted-record digest and provenance, and reproducible schema-evidence metadata. The adapter under `internal/execution/openshell` additionally requires the installed CLI to report OpenShell `0.0.86` before a caller admits live work.

## Pinned inputs and provenance

The profile pins OpenShell `v0.0.86` at commit `d556748771c41cbbd4e4dd7cd9030c798afe2b7d`, its gateway and supervisor multi-architecture image indexes, and the OpenShell Community base image at repository commit `fffb6b2248ff6ba585f50517f3711b08122089f2`. That base image contains Codex `0.117.0`, so this is the first runtime version under review even though newer Codex releases may exist.

The deny-all fixture is copied byte-for-byte from `crates/openshell-prover/testdata/empty-policy.yaml` in the pinned OpenShell release. Its SHA-256 digest is recorded in the profile and checked on every `pnpm verify`. It permits negative and lifecycle conformance work without creating a Cedar-to-OpenShell translator. It does not replace Rosetta and is never production-certifiable.

The Codex provider profile digest records the upstream `providers/codex.yaml` input. It is evidence for a later live test, not an authorization to place credentials in DataGround configuration, environment variables, command arguments, logs, or sandbox files. The closed evidence path owns temporary provider provisioning; ordinary development and production provider creation remain deployment responsibilities.

Credential non-exposure evidence has a closed, versioned contract at [`deploy/openshell/credential-non-exposure-evidence.schema.json`](../../deploy/openshell/credential-non-exposure-evidence.schema.json). A live verifier must use a fresh high-entropy canary instead of a real provider secret and retain only its SHA-256 commitment. The version-3 record binds the run to the exact OpenShell commit, gateway, supervisor and sandbox image digests, provider-profile source digest, Codex version, loopback endpoint, Docker driver, checked Compose and gateway-configuration digests, and profile-owned `dataground-openshell-canary` verifier identity at version `3.0.0`. Run and scan intervals use canonical UTC timestamps. It must report complete zero-match inspection of sandbox processes, environment and filesystem; provider arguments; gateway and sandbox logs; and runtime errors. Sandbox, temporary provider binding and verifier workspace cleanup must all be confirmed.

Validate any record with `pnpm openshell:credential-evidence:check <evidence.json>`, or validate the incorporated record with `pnpm openshell:credential-evidence:accepted:check`. Schema validity alone does not certify the boundary: duplicate or missing surfaces, profile drift, positive matches, partial scans, insufficient coverage, uncertain cleanup and out-of-order timestamps fail verification. The accepted record contains only commitments, content-free scan metrics, portable resource identities and cleanup receipts; canary plaintext, provider credentials, environment snapshots, process dumps, filesystem content, arguments, logs and error payloads must never be committed. Repository verification checks both negative verifier cases and the exact digest-bound accepted record. This certification does not unblock full runtime or production use.

The live harness must generate canaries as `dataground-canary-v1:` followed by exactly 32 random bytes encoded as 43 characters of unpadded base64url. `go run ./cmd/dataground-openshell-canary-scan --surface <surface> --run-id <32-lowercase-hex> --resource-name <live-resource> --commitment sha256:<digest> --max-bytes <profile-limit>` scans a bounded byte stream using only that commitment and emits the closed report defined by [`deploy/openshell/credential-canary-scan.schema.json`](../../deploy/openshell/credential-canary-scan.schema.json). The command delegates complete report production to the profile-owned `internal/security/canaryscan.ScanReport` boundary. That path validates the closed run and resource context before reading, recognizes the public prefix, hashes only complete structured candidates, derives the resource kind, timestamps the observation, selects the fail-closed status, and binds the exact inspected bytes under the `dataground.openshell-canary-input/v1` domain without returning candidate bytes. Each accepted evidence check must preserve that complete report, including its schema version, inspected-byte count, candidate count, and start and finish timestamps. The checked development profile owns one explicit maximum and minimum inspected-byte expectation for each of the seven surfaces; evidence outside either bound fails verification. Zero is permitted only where the profile explicitly treats an empty successful stream as meaningful. Filesystem inspection first requires the pinned base image's `/etc/os-release` anchor, then traverses regular files across mounted filesystems while excluding the exact virtual kernel roots `/proc` and `/sys`; it does not follow symbolic links, and the source fails unless the required anchor contributes inspected bytes.

The internal collector at `internal/security/canarycollect` now owns the boundary between source acquisition and scanning. It validates the complete seven-source plan, run and resource identities, and profile limits before any source is opened; acquires each source exactly once in the profile's canonical order; passes the open stream directly to `canaryscan.ScanReport`; closes it before continuing; and returns an opaque ordered collection. Missing, duplicate, unknown, unreadable, partially read, canary-bearing, or uncertain-close sources fail the collection without exposing upstream errors or source content. Partial collections retain only scanner-owned reports internally for diagnosis and refuse JSON serialization, so they cannot become final evidence even when their individual reports are clear.

The final run boundary at `internal/security/canaryevidence` now owns the checked profile snapshot, verifier identity, run interval, resource bindings, cleanup order and receipts, and final JSON assembly. It validates the entire source and cleanup plan before side effects, runs cleanup for the exact sandbox, provider binding, and verifier workspace even after collection failure or cancellation, and refuses serialization unless collection and every cleanup step succeed. Callers cannot supply profile fields, timestamps, verifier fields, cleanup statuses, or a result value.

The verifier workspace adapter at `internal/security/canaryworkspace` creates exactly one fresh `dg-canary-<runID>` directory beneath a pre-existing deployment-owned mode-`0700` parent. It never exposes the host path, cannot serialize, rejects reuse or ambiguous disappearance, accepts cleanup only for the exact run-owned identity, and removes only an empty workspace before synchronizing the parent directory. Unexpected content remains untouched and prevents a cleanup receipt.

The sandbox cleanup adapter at `internal/security/canarysandbox` binds one evidence run to the exact DataGround execution returned by the OpenShell provider. It exposes only that portable execution ID to the evidence record, never the native sandbox name or gateway coordinates. Cleanup terminates the persisted execution through the provider boundary and then requires a timestamped exact terminal observation; provider errors are sanitized, mismatched or nonterminal observations remain uncertain, successful cleanup is concurrency-safe and idempotent, and adapter state cannot serialize.

The provider provisioner at `internal/security/canaryprovider` generates the structured canary from 32 bytes of cryptographic entropy, derives only its SHA-256 commitment, and creates the exact `dg-canary-provider-<runID>` Codex binding through the pinned OpenShell boundary. All four profile credential slots receive the same canary through bare credential keys in an isolated child environment, so the plaintext never enters the OpenShell argument vector or the returned provisioned state. The temporary canary buffer is cleared before the provisioner returns, and provisioned state cannot serialize.

The provider cleanup adapter at `internal/security/canaryprovider` binds the evidence run to a temporary `dg-canary-provider-<runID>` binding and the exact OpenShell provider ID, resource version, isolation domain, and gateway returned at creation. The adapter is concurrency-safe, idempotent, and non-serializable; native provider and gateway identities do not enter evidence.

The source acquisition adapter at `internal/security/canarysource` now binds the complete plan to the exact run, canary commitment, and portable gateway, sandbox, provider, and runtime names before acquisition. It exposes separate typed OpenShell, Docker, and runtime source ports, owns the canonical seven-source routing, permits only one collection attempt, passes each stream directly into the collector, sanitizes backend failures, closes ambiguous streams, and cannot serialize. The OpenShell source backend at `internal/execution/openshell` resolves the exact persisted execution to its protected native sandbox and gateway coordinates before construction, requires the execution to be ready, verifies the configured CLI is exactly OpenShell `0.0.86`, and revalidates that private target before every source is opened. Calls must follow the adapter's source order even across copied values, native command failures are sanitized, incomplete reads terminate the command, and the backend cannot serialize. The filesystem source requires `/etc/os-release`, traverses regular files across mounted filesystems, excludes only the exact virtual kernel roots `/proc` and `/sys`, and does not follow symbolic links; the separate process and log sources cover procfs and the authoritative OpenShell log files.

The Docker source backend at `internal/security/canarydocker` resolves the Docker executable once, then binds one exact running gateway container by its immutable container ID, digest-pinned gateway image, Compose project and `gateway` service labels, and run-specific gateway and provider evidence labels. It therefore observes the same stderr stream without exposing or reconstructing a native invocation identity. The closed composition boundary at `internal/security/canaryharness` now derives the portable gateway, provider, runtime, and workspace names from the exact run; accepts only the repository-owned provisioned binding, ready execution, verifier workspace, concrete OpenShell, Docker, and runtime backends, and OpenShell provider; constructs the source and cleanup adapters once; and binds them to the sealed evidence run. Harness copies share one irreversible start state, identity drift fails before collection, and state cannot serialize. After the first six canonical live surfaces, the harness closes the exact wrapped runtime once so stderr can reach EOF before the seventh scan; rejected composition clears an already completed capture, and every attempted run discards any capture left unopened by an earlier source failure.

## Development topology

The initial live topology is one host-loopback-only OpenShell gateway using the Docker compute driver. The gateway container shares the Docker host network namespace so OpenShell can bind its driver-owned listener on the sandbox bridge; its control and health listeners remain restricted to `127.0.0.1` on ports `8080` and `8081`. The DataGround API uses port `8082`, keeping all three checked development listeners distinct. Launcher readiness is bound to the gateway's dependency-aware `/readyz` route; the health listener root is not a valid readiness signal. Docker Compose mounts the Docker socket and `/var/lib/openshell`; this grants the gateway substantial control over the development host and is unsuitable for an untrusted or shared machine. The gateway uses plaintext transport and accepts unauthenticated user CLI calls only on the dedicated loopback listener; sandbox supervisors still require the fresh run-scoped gateway JWT. The provider contract supports multiple registered gateways and durable selection, but production gateway identity, TLS, richer placement constraints, and deployment wiring remain separate work.

On a Docker-capable development host with OpenShell CLI `0.0.86` installed:

```shell
pnpm openshell:profile:check
pnpm openshell:local:up
curl --fail http://127.0.0.1:8081/readyz
openshell --gateway-endpoint http://127.0.0.1:8080 status
```

The ordinary development command uses `deploy/openshell/local/docker-compose.yml` and the exact digest-pinned images from the checked development profile. Its wrapper requires the exact OpenShell CLI version and creates or validates one persistent Ed25519 gateway-JWT keypair under the current user's owner-only local state directory; key files are never stored in the repository. It runs the gateway as root with access to the Docker socket and retains its SQLite database and extracted supervisor under the Docker host's `/var/lib/openshell`; use it only on a trusted local development machine. This topology is not evidence-producing. The credential and runtime conformance Compose files remain launcher-owned and intentionally reject direct startup without fresh run-scoped state, identity, and JWT inputs.

CI separately starts the checked runtime-conformance gateway, verifies its exact image, container and run labels through Docker's actual inspection template, and observes complete teardown without using provider credentials or producing runtime evidence. On an isolated Linux Docker host with ports 8080 and 8081 free, run `DATAGROUND_TEST_RUNTIME_TOPOLOGY_ROOT="$PWD" go test ./internal/execution/runtimeevidence -run '^TestDockerTopologyLiveIdentityAndCleanup$' -count=1 -timeout=6m`. The test owns a random Compose project and private temporary workspace. The checked host-network topology requires a Linux execution environment; running it directly on a macOS host is unsupported.

The checked-in profile deliberately does not create a provider or run a credential-bearing agent. A deny-all sandbox can be used for lifecycle conformance without provider access:

```shell
openshell --gateway-endpoint http://127.0.0.1:8080 sandbox create \
  --name dg-deny-all \
  --from ghcr.io/nvidia/openshell-community/sandboxes/base@sha256:aeef1c63f00e2913ea002ccb3aaf925f338b5c5d70e63576f0d95c16a138044e \
  --policy deploy/openshell/policies/deny-all.yaml \
  --no-auto-providers \
  --approval-mode manual \
  -- true
```

For a real, billable local inference smoke test, first sign in with the pinned Codex CLI so an owner-only ChatGPT authentication file exists at `$CODEX_HOME/auth.json` or `~/.codex/auth.json`, then run:

```shell
DATAGROUND_CODEX_SMOKE_MODEL="<available-model-id>" pnpm openshell:local:codex-smoke
```

Choose a model available to the local account explicitly; the command has no default or fallback model. The model identifier must contain 1–128 ASCII letters, digits, dots, underscores, or hyphens and begin with a letter or digit. Invalid or missing selections fail before credential access or gateway changes.

The smoke command requires the running loopback gateway and exact OpenShell `0.0.86` CLI. It enables provider profiles, lints and installs the checked `dataground-codex-chatgpt` bridge profile, and imports only the short-lived access token and account identifier into a persistent local OpenShell provider through a scrubbed child environment. Credential values are never command arguments or command output. It then creates a randomly named, digest-pinned, deny-all sandbox; runs one locked, read-only, ephemeral Codex turn using the selected model through the ChatGPT Codex endpoint; requires the exact `dataground-openshell-e2e-ok` response; and verifies that the sandbox was removed.

The bridge is necessary because the upstream OpenShell Codex profile exposes OAuth fields under `CODEX_AUTH_*`, while the pinned Codex `0.117.0` default model provider does not consume those environment variables. The checked smoke command instead fixes the ChatGPT endpoint, account header, Responses wire protocol, and environment placeholders explicitly. It neither stores credentials in the repository nor imports the refresh or identity token. Re-run the command to refresh the local provider from the current authentication file.

This smoke proves only one ordinary local OpenShell-to-Codex inference path. It does not produce runtime-conformance evidence, activate a runtime-certification manifest, exercise the governed development worker, or change production-certification status.

Stop the local gateway with `pnpm openshell:local:down`. This removes the gateway container but leaves OpenShell state under `/var/lib/openshell`; do not delete that directory as part of routine cleanup.

## Adapter behavior and remaining gates

The development adapter registers gateways, selects only active gateways with required capabilities, reserves deterministic placements, creates deterministic sandboxes, observes ambiguous creation and termination before repetition, starts Codex app-server through non-TTY stdio, retrieves logs, exports files, terminates sandboxes, and lists managed orphans. It invokes the OpenShell binary directly with an argument vector rather than through a shell. Gateway endpoints and native sandbox names remain in protected provider state; returned resources and runtime sessions cannot serialize them.

Runtime startup requires a ready execution on the exact Docker gateway `http://127.0.0.1:8080`, rechecks the pinned CLI version and execution scope, then starts the CLI’s named `ssh-proxy` with a fixed argument vector. A private Go SSH session carries `codex app-server` without a PTY, preserving duplex stdin/stdout and separate stderr. It never uses a direct SSH network dialer or user SSH configuration. OpenShell 0.0.86 authorizes the named sandbox tunnel but publishes no host-key fingerprint; peer identity therefore relies on the loopback gateway’s authorization, matching the upstream SSH client’s trust assumption. This is a development transport, not independently pinned SSH host identity or production ingress certification. Setup and cancellation are bounded, proxy diagnostics remain private and bounded, and shutdown requires a successful remote exit receipt before reporting confirmed termination.

The Codex adapter under `internal/runtime/codex` performs the stable `initialize`/`initialized`, thread-start, turn-start, and turn-interrupt exchange against bounded JSONL streams. It normalizes lifecycle, assistant text, item activity, and approval requests without exposing native identifiers. Approval requests receive opaque adapter IDs and remain unanswered until an explicit decision; locked mode denies them without creating an actionable event. Terminal notifications, explicit interruption requests and transport shutdown retire outstanding approval handles. The pinned `serverRequest/resolved` notification retires only the matching native request in the current thread; malformed or cross-thread clearance fails closed. Request identity uses decoded string or int64 values so equivalent JSON spellings cannot create separate approval handles. Decisions queued behind the protocol writer recheck that the handle is still active before beginning their write; a failed or invalidated write cannot restore an expired handle. Approval and sandbox defaults are locked and read-only. Permission-escalation, rich item-delta, usage, resume/steer, and artifact normalization remain outside this initial protocol surface and must not be advertised as supported. Question handling has a separate internal opt-in described below and remains unsupported by the governed worker. An opt-in claim-bound reconciler driver can compose a ready admitted execution, a profile-aware request mapper, explicit runtime authorization, the single-use attempt guard, lease renewal, normalized events, durable interactive approval mediation, and artifact finalization with this adapter. Interactive mode is accepted only when the durable approval store and exact-revision authorizer are configured together; incomplete composition fails before runtime use. The governed development worker supplies that complete boundary, while reference behavior remains unchanged. Approval resolution records the actual principal after entry authorization, and delivery reauthorizes immediately before reserving one native acknowledgement; an ambiguous post-reservation failure is never retried. Successful turns materialize only acknowledged text deltas into a bounded declared result. Structured output schemas compile before provider access with a pinned JSON Schema 2020-12 default and no external resource loading; the result must decode as exactly one conforming JSON value, while missing, malformed, non-conforming, or oversized output records a terminal runtime failure without repeating the native turn. The governed development composition also owns the invocation-artifact finalizer, PostgreSQL catalog, S3 transport, and OpenShell export-content boundary for its exact certified target. OpenShell export accepts only a clean absolute sandbox path, chooses a private host destination inside an exclusively owned workspace, bounds and validates the downloaded file, and removes it before returning non-serializable bytes. Default/public runtime composition and production artifact transport remain separate work.

The provider accepts a replaceable state store. Its in-memory implementation is for focused conformance tests only. The PostgreSQL implementation persists isolation-scoped gateway registrations, capabilities, endpoints, drain and loss state, placement reservations, native sandbox routing, observed execution state, and released capacity across provider restarts. Registration and placement retries are idempotent only when immutable inputs match; conflicting retries fail closed. A lost gateway marks its nonterminal executions unknown and its active placements lost instead of reassigning a running sandbox.

Schema migration `00002_execution_placement.sql` establishes this protected routing state. The store is exercised with PostgreSQL integration tests, but it is not yet connected to a public admission command or a production reconciler. Gateway credentials, health leases, capacity signals, locality, policy/runtime compatibility, migration, and stuck-reservation repair remain future placement work.

The adapter can explicitly enable the pinned experimental question protocol with `QuestionMode: QuestionInteractive` and a positive `QuestionTimeout` no longer than 15 minutes. It normalizes one to three plain-text questions, two to four labelled options or explicitly enabled free text, and opaque item/option IDs. The shared domain validator also represents multi-select, while the pinned Codex request maps only single selection. Every answer must cover the exact request, choose only its frozen options or permitted free text, and fit the bounded text limits. Secret-input requests, unknown fields, malformed scopes, concurrent question bundles and unsupported shapes are rejected without exposing native identifiers. Request clearance, interruption, completion and closure retire pending questions; expiry closes the transport without inventing an answer.

Schema migration 50 adds an internal durable question ledger. Requests bind their immutable prompts and expiry to one isolation domain, invocation, exact service revision, runtime effect and source sequence. Answer acceptance requires an explicit entry authorizer; delivery reservation requires a separate effect authorizer, the original runtime attempt and a current worker lease. Exact answer retries retain the original actor and correlation, reauthorize the read, and cannot alter the answer. Delivery permission is consumed once: an acknowledgement can mark it delivered, while closure or expiry after reservation records `delivery_unknown` and never grants another send. A bounded, isolation-scoped database-clock sweep persists expiry even after the runtime lease ends. Changes commit safe audit and outbox records together; the requested event carries only the question ID, version and expiry. Prompts and answers remain internal and require a separate authorized projection. Retained question records prevent downgrade; use forward repair after this boundary is exercised.

The adapter and durable ledger are separate internal components. The claim-bound driver rejects question mode before reserving or starting a runtime until policy resolution and decision audit, answer delivery, expiry ownership, public APIs and the Workbench are composed. The default request remains question-disabled, runtime capability evidence still classifies questions as unsupported, and no live question conformance is claimed. The checked Codex 0.117.0 schema pins the native shapes; the [official app-server documentation](https://learn.chatgpt.com/docs/app-server) describes experimental user-input and request-clearance behavior.

## Immutable execution plans

The internal `dataground.execution-plan/v1` contract is the portable input to future admission and reconciliation. It binds one isolation-scoped service revision to its runtime profile and required capabilities, an environment revision and immutable OCI image, environment-manifest digest, enforcement-bundle identifier and digest, provider-profile names, and certified runtime-matrix identifier and digest. Lists are normalized before the plan is hashed and stored. A service revision can receive one plan: an identical retry succeeds, while any replacement fails closed.

The binding validates that the runtime profile and capabilities exactly match the referenced service revision. PostgreSQL persists it through `00003_execution_plan.sql`, cascades it when the revision is deleted, and records the successful binding in the audit log in the same transaction. Isolation-domain scope is part of both the primary key and foreign key. The public v1 API is unchanged.

An enforcement-bundle identifier is not a filesystem path. Schema migration `00004_enforcement_bundle.sql` adds an append-only, isolation-scoped catalog for the artifact's size, digest, deterministic logical object key, and recorded Rosetta provenance. Identical retries are idempotent, conflicting replacements fail closed, revision deletion cascades, and the first successful binding is audited in the same transaction. Object keys have the form `enforcement-bundles/v1/<domain>/<revision>/<bundle>/<digest>.yaml`; they are protected routing state and never public resource or audit metadata.

The object-backed source depends on a read-only catalog and a narrow platform-object reader. It derives the key rather than accepting one from a caller, caps every read at the policy-size limit, closes the stream, and reverifies the recorded byte count and SHA-256 digest before returning owned bytes. A metadata record whose object is absent is treated as storage unavailability, because the append-only catalog says that object should exist. Internal execution admission then requires the bundle to match the plan's domain, revision, identifier, and digest before placement. Provider profiles are names, not embedded provider configuration or credentials. The OpenShell adapter resolves every requested name through an immutable deployment-owned registry before provider access; malformed or unregistered profiles fail closed, and empty selection never enables a fallback profile. The plan deliberately contains no gateway endpoint, sandbox name, native runtime identifier, local policy path, object key, or secret.

The write-side finalizer accepts only a normalized record, validated policy bytes and audit correlation. Its object adapter must conditionally create the deterministic key without overwrite and consume the supplied stream synchronously. Every response, including a write error or precondition conflict, is followed by a bounded read-back and exact digest, size and byte comparison before PostgreSQL metadata can bind. This observation recovers a lost acknowledgement or identical retry without repeating a destructive effect. The finalizer has no delete authority: a database failure may leave an unreachable deterministic object for a later retry to adopt, but cannot delete content that another retry may already have bound. Content and object keys remain excluded from serialization and audit metadata.

The OpenShell provider no longer accepts a caller-controlled policy path. It labels the sandbox with an opaque fingerprint of the immutable image, policy digest, normalized provider profiles, isolation domain, and operation; observation recovers a lost acknowledgement only when that fingerprint matches, while a conflicting retry fails closed. The pinned OpenShell CLI reads `--policy` only from a named file, so a new sandbox requires an explicitly opened `PolicyWorkspace`. The workspace must be a dedicated absolute mode-`0700` directory. It holds an advisory process lock, accepts no unrelated content, writes verified policy bytes to mode-`0600` files, syncs creation and deletion, and removes the file after the synchronous CLI call.

Opening the workspace after a worker crash acquires the released Unix advisory lock and removes only single-link regular mode-`0600` files owned by the worker user and carrying DataGround's enforcement-policy prefix. A concurrent owner, mismatched ownership, a symlinked workspace or lock, hard links, unsafe permissions, or unexpected entries fail closed; the cleanup never recursively deletes the directory. Closing a workspace while a policy is active also fails. Deployment wiring must create one private workspace per worker ownership domain on its Unix runtime, open it before constructing a provider, retain it for the worker lifetime, and close it during orderly shutdown. Calls that only observe an existing deterministic sandbox do not need to rematerialize its policy, but creation of a previously absent sandbox cannot proceed without the workspace.

Admission and finalization remain internal. Invocation state-machine version 2 has a distinct start effect and an optional driver that resolves its persisted service, revision, principal and correlation scope, requires explicit consequential-effect authorization, observes an execution by operation, and then invokes admission. A repaired version 2 operation uses its separately persisted repair principal and correlation while retaining the original request identity; unresolved legacy repairs fail closed. Existing version 1 operations retain their single reference effect and are rejected by the optional admission driver. Reference mode continues to route version 2 effects to the deterministic driver. The explicit `governed-development` worker mode owns admission, claim-bound runtime, and cancellation together for one configured isolation domain. The logical object ports, finalizer, PostgreSQL catalog, and narrow S3 REST adapter exist, but there is no certified backend, bucket or workload-identity configuration, public admission API, production/default governed composition, or certified live sandbox service through this path. The adapter requires an explicit operator-supplied transport, blocks redirects, permits plain HTTP only for an explicitly enabled loopback endpoint, and exposes only safe missing/conflict outcomes. The eventual deployment transport must add workload authentication; that behavior is not implemented or certified here. Persisted provenance is evidence, not authorization or Rosetta certification. Missing plans, cross-domain or revision-mismatched bundles, malformed identities, digest mismatches, absent or unavailable objects, unavailable placement, missing or unsafe policy workspace, and cancelled provider calls fail closed. Rosetta certification and production object storage remain separate gates.
