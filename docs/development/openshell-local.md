# Local OpenShell execution boundary

DataGround's first OpenShell development profile is pinned and internally consistent, but it is not a complete runtime or production certification. The profile establishes the Docker gateway topology, immutable OCI inputs, an upstream deny-all policy fixture, the internal `ExecutionProvider` port, and the Codex app-server JSONL-over-stdio transport. The internal Codex adapter has protocol-level conformance coverage for its initial lifecycle, event, interruption, and approval surface. Provider-secret non-exposure is certified only for this exact pinned development profile by the incorporated coverage-qualified v3 record.

The machine-readable profile is [`deploy/openshell/development-profile.json`](../../deploy/openshell/development-profile.json), and its accepted record is [`deploy/openshell/evidence/openshell-credential-non-exposure-v3.json`](../../deploy/openshell/evidence/openshell-credential-non-exposure-v3.json). `pnpm openshell:profile:check` verifies the immutable image references, loopback topology, deny-all fixture hash, production-blocked state, runtime transport, accepted-record digest and provenance, and reproducible schema-evidence metadata. The adapter under `internal/execution/openshell` additionally requires the installed CLI to report OpenShell `0.0.86` before a caller admits live work.

## Pinned inputs and provenance

The profile pins OpenShell `v0.0.86` at commit `d556748771c41cbbd4e4dd7cd9030c798afe2b7d`, its gateway and supervisor multi-architecture image indexes, and the OpenShell Community base image at repository commit `fffb6b2248ff6ba585f50517f3711b08122089f2`. That base image contains Codex `0.117.0`, so this is the first runtime version under review even though newer Codex releases may exist.

The deny-all fixture is copied byte-for-byte from `crates/openshell-prover/testdata/empty-policy.yaml` in the pinned OpenShell release. Its SHA-256 digest is recorded in the profile and checked on every `pnpm verify`. It permits negative and lifecycle conformance work without creating a Cedar-to-OpenShell translator. It does not replace Rosetta and is never production-certifiable.

The Codex provider profile digest records the upstream `providers/codex.yaml` input. It is evidence for a later live test, not an authorization to place credentials in DataGround configuration, environment variables, command arguments, logs, or sandbox files. The closed evidence path owns temporary provider provisioning; ordinary development and production provider creation remain deployment responsibilities.

Credential non-exposure evidence has a closed, versioned contract at [`deploy/openshell/credential-non-exposure-evidence.schema.json`](../../deploy/openshell/credential-non-exposure-evidence.schema.json). A live verifier must use a fresh high-entropy canary instead of a real provider secret and retain only its SHA-256 commitment. The version-3 record binds the run to the exact OpenShell commit, gateway, supervisor and sandbox image digests, provider-profile source digest, Codex version, loopback endpoint, Docker driver, checked Compose and gateway-configuration digests, and profile-owned `dataground-openshell-canary` verifier identity at version `3.0.0`. Run and scan intervals use canonical UTC timestamps. It must report complete zero-match inspection of sandbox processes, environment and filesystem; provider arguments; gateway and sandbox logs; and runtime errors. Sandbox, temporary provider binding and verifier workspace cleanup must all be confirmed.

Validate any record with `pnpm openshell:credential-evidence:check <evidence.json>`, or validate the incorporated record with `pnpm openshell:credential-evidence:accepted:check`. Schema validity alone does not certify the boundary: duplicate or missing surfaces, profile drift, positive matches, partial scans, insufficient coverage, uncertain cleanup and out-of-order timestamps fail verification. The accepted record contains only commitments, content-free scan metrics, portable resource identities and cleanup receipts; canary plaintext, provider credentials, environment snapshots, process dumps, filesystem content, arguments, logs and error payloads must never be committed. Repository verification checks both negative verifier cases and the exact digest-bound accepted record. This certification does not unblock full runtime or production use.

The live harness must generate canaries as `dataground-canary-v1:` followed by exactly 32 random bytes encoded as 43 characters of unpadded base64url. `go run ./cmd/dataground-openshell-canary-scan --surface <surface> --run-id <32-lowercase-hex> --resource-name <live-resource> --commitment sha256:<digest> --max-bytes <profile-limit>` scans a bounded byte stream using only that commitment and emits the closed report defined by [`deploy/openshell/credential-canary-scan.schema.json`](../../deploy/openshell/credential-canary-scan.schema.json). The command delegates complete report production to the profile-owned `internal/security/canaryscan.ScanReport` boundary. That path validates the closed run and resource context before reading, recognizes the public prefix, hashes only complete structured candidates, derives the resource kind, timestamps the observation, selects the fail-closed status, and binds the exact inspected bytes under the `dataground.openshell-canary-input/v1` domain without returning candidate bytes. Each accepted evidence check must preserve that complete report, including its schema version, inspected-byte count, candidate count, and start and finish timestamps. The checked development profile owns one explicit maximum and minimum inspected-byte expectation for each of the seven surfaces; evidence outside either bound fails verification. Zero is permitted only where the profile explicitly treats an empty successful stream as meaningful. Filesystem inspection first requires the pinned base image's `/etc/os-release` anchor, then traverses regular files across mounted filesystems while excluding the exact virtual kernel roots `/proc` and `/sys`; it does not follow symbolic links, and the source fails unless the required anchor contributes inspected bytes.

The internal collector at `internal/security/canarycollect` now owns the boundary between source acquisition and scanning. It validates the complete seven-source plan, run and resource identities, and profile limits before any source is opened; acquires each source exactly once in the profile's canonical order; passes the open stream directly to `canaryscan.ScanReport`; closes it before continuing; and returns an opaque ordered collection. Missing, duplicate, unknown, unreadable, partially read, canary-bearing, or uncertain-close sources fail the collection without exposing upstream errors or source content. Partial collections retain only scanner-owned reports internally for diagnosis and refuse JSON serialization, so they cannot become final evidence even when their individual reports are clear.

The final run boundary at `internal/security/canaryevidence` now owns the checked profile snapshot, verifier identity, run interval, resource bindings, cleanup order and receipts, and final JSON assembly. It validates the entire source and cleanup plan before side effects, runs cleanup for the exact sandbox, provider binding, and verifier workspace even after collection failure or cancellation, and refuses serialization unless collection and every cleanup step succeed. Callers cannot supply profile fields, timestamps, verifier fields, cleanup statuses, or a result value.

The verifier workspace adapter at `internal/security/canaryworkspace` creates exactly one fresh `dg-canary-<runID>` directory beneath a pre-existing deployment-owned mode-`0700` parent. It never exposes the host path, cannot serialize, rejects reuse or ambiguous disappearance, accepts cleanup only for the exact run-owned identity, and removes only an empty workspace before synchronizing the parent directory. Unexpected content remains untouched and prevents a cleanup receipt.

The sandbox cleanup adapter at `internal/security/canarysandbox` binds one evidence run to the exact DataGround execution returned by the OpenShell provider. It exposes only that portable execution ID to the evidence record, never the native sandbox name or gateway coordinates. Cleanup terminates the persisted execution through the provider boundary and then requires a timestamped exact terminal observation; provider errors are sanitized, mismatched or nonterminal observations remain uncertain, successful cleanup is concurrency-safe and idempotent, and adapter state cannot serialize.

The provider provisioner at `internal/security/canaryprovider` generates the structured canary from 32 bytes of cryptographic entropy, derives only its SHA-256 commitment, and creates the exact `dg-canary-provider-<runID>` Codex binding through the pinned OpenShell boundary. All four profile credential slots receive the same canary through bare credential keys in an isolated child environment, so the plaintext never enters the OpenShell argument vector or the returned provisioned state. Creation requires prior absence on the dedicated evidence gateway and accepts a lost acknowledgement only when credential-safe metadata proves the expected name, type, credential-key set, immutable ID, and resource version afterward. The temporary canary buffer is cleared before the provisioner returns, and provisioned state cannot serialize.

The provider cleanup adapter at `internal/security/canaryprovider` binds the evidence run to a temporary `dg-canary-provider-<runID>` binding and the exact OpenShell provider ID, resource version, isolation domain, and gateway returned at creation. The concrete OpenShell boundary reads only credential-safe structured provider metadata from that persisted gateway, observes the exact identity before deletion, rejects a replacement under the same name, and requires timestamped absence afterward. Delete acknowledgement loss converges only through observed absence. Because pinned OpenShell deletion is name-addressed rather than compare-and-delete, the live run requires a dedicated evidence gateway with no concurrent provider mutation; the run-derived name and pre/post observations do not claim protection from a privileged racing operator. The adapter is concurrency-safe, idempotent, and non-serializable; native provider and gateway identities do not enter evidence.

The source acquisition adapter at `internal/security/canarysource` now binds the complete plan to the exact run, canary commitment, and portable gateway, sandbox, provider, and runtime names before acquisition. It exposes separate typed OpenShell, Docker, and runtime source ports, owns the canonical seven-source routing, permits only one collection attempt, passes each stream directly into the collector, sanitizes backend failures, closes ambiguous streams, and cannot serialize. A cancelled or failed attempt consumes the adapter because live streams cannot be assumed replayable.

The OpenShell source backend at `internal/execution/openshell` resolves the exact persisted execution to its protected native sandbox and gateway coordinates before construction, requires the execution to be ready, verifies the configured CLI is exactly OpenShell `0.0.86`, and revalidates that private target before every source is opened. It streams process command lines, process environments, the sandbox root filesystem, and the complete on-sandbox OpenShell log files through fixed `sandbox exec --no-tty` argument vectors without invoking a shell. Calls must follow the adapter's source order even across copied values, native command failures are sanitized, incomplete reads terminate the command, and the backend cannot serialize. The filesystem source requires `/etc/os-release`, traverses regular files across mounted filesystems, excludes only the exact virtual kernel roots `/proc` and `/sys`, and does not follow symbolic links; the separate process and log sources cover procfs and the authoritative OpenShell log files.

The Docker source backend at `internal/security/canarydocker` resolves the Docker executable once, then binds one exact running gateway container by its immutable container ID, digest-pinned gateway image, Compose project and `gateway` service labels, and run-specific gateway and provider evidence labels. Before each read it re-inspects only that credential-safe metadata. Provider evidence streams the gateway entrypoint and argument vector, while gateway evidence streams the container's complete timestamped stdout and stderr logs; both use the exact container ID and fixed Docker argument vectors without a shell. Copies share source order and failure state, and target drift, overlap, incomplete reads, cancellation, and native command failure permanently fail the backend without exposing Docker diagnostics or retaining source bytes. A certifying Compose start must set `DATAGROUND_CREDENTIAL_EVIDENCE_RUN_ID`, `DATAGROUND_CREDENTIAL_EVIDENCE_GATEWAY`, and `DATAGROUND_CREDENTIAL_EVIDENCE_PROVIDER` to the same portable identities bound by the run; their empty defaults deliberately leave an ordinary development start ineligible for evidence.

The runtime source backend at `internal/security/canaryruntime` wraps the exact `execution.RuntimeSession` before that session is passed to the native runtime adapter. It therefore observes the same stderr stream without exposing or reconstructing a native invocation identity. Capture is bound to the evidence run and portable runtime name, held only in bounded memory, and made available after a complete terminal drain for one scanner handoff. The adapter continues draining after the 16 MiB limit so the native process cannot block, but overflow, duplicate consumers, target drift, incomplete reads, capture errors, or cancellation permanently fail evidence. Captured bytes are cleared when scanner ownership closes or a handoff becomes unusable, and the wrapper cannot serialize. The harness must defer `Discard` so a failure in any earlier canonical source also clears a completed but unopened runtime capture.

The closed composition boundary at `internal/security/canaryharness` now derives the portable gateway, provider, runtime, and workspace names from the exact run; accepts only the repository-owned provisioned binding, ready execution, verifier workspace, concrete OpenShell, Docker, and runtime backends, and OpenShell provider; constructs the source and cleanup adapters once; and binds them to the sealed evidence run. Harness copies share one irreversible start state, identity drift fails before collection, and state cannot serialize. After the first six canonical live surfaces, the harness closes the exact wrapped runtime once so stderr can reach EOF before the seventh scan; rejected composition clears an already completed capture, and every attempted run discards any capture left unopened by an earlier source failure.

The Docker-hosted launcher at `internal/security/canarylauncher` now generates the fresh run nonce, verifies the exact checked Compose, gateway and deny-all policy inputs, freezes the Compose and gateway bytes into a private run-owned directory before mutation, starts a dedicated run-derived Compose project, invokes the owned provisioner, creates and observes the provider-bound sandbox, wraps the exact runtime session before Codex client construction, and passes those live resources into the closed composition boundary. Gateway state uses a run-private directory bind-mounted at the identical host and container path; the launcher generates a fresh Ed25519 gateway JWT keypair and identifier in the private topology workspace, mounts those files read-only, and removes them before releasing evidence. The gateway runs as the invoking user plus only the Docker-socket group, with allowlisted child environments; the deterministic sandbox route is persisted before native creation. Evidence is withheld unless sandbox, provider, verifier workspace, gateway container, named volume and frozen topology cleanup all succeed. Run it from the repository root with `pnpm openshell:credential-evidence:run -- --workspace-root <owner-only-mode-0700-directory>`. The command writes only the final JSON record to stdout and emits a generic failure on stderr.

Repository tests validate launcher wiring and failure boundaries but do not execute Docker. The dedicated `.github/workflows/openshell-credential-evidence.yml` workflow installs the exact pinned OpenShell release from its immutable upstream source, runs the launcher on an isolated Docker-capable runner, verifies the resulting coverage-qualified v3 record, independently rejects residual run-scoped containers, volumes, or workspaces, and uploads only a verified record. The workflow uses read-only repository permissions and no provider or repository secrets. Workflow run `30568233656` produced the accepted record incorporated here; its exact bytes, SHA-256, head commit, workflow identity, artifact identity and archive digest are profile-bound. Later workflow runs are regression evidence and do not silently replace the accepted record.

Codex schema generation does not produce byte-stable aggregate files because definition order can vary between runs. The profile therefore records a SHA-256 digest after recursive object-key ordering and compact JSON serialization. Regenerate the schema twice and verify either directory with `pnpm codex:schema:check <directory>`; the check also confirms the required initial methods and server requests remain present.

## Development topology

The initial live topology is one host-loopback-only OpenShell gateway using the Docker compute driver. The gateway container shares the Docker host network namespace so OpenShell can bind its driver-owned listener on the sandbox bridge; its control and health listeners remain restricted to `127.0.0.1`. Launcher readiness is bound to the gateway's dependency-aware `/readyz` route; the health listener root is not a valid readiness signal. Docker Compose mounts the Docker socket and `/var/lib/openshell`; this grants the gateway substantial control over the development host and is unsuitable for an untrusted or shared machine. The gateway uses plaintext transport and accepts unauthenticated user CLI calls only on the dedicated loopback listener; sandbox supervisors still require the fresh run-scoped gateway JWT. The provider contract supports multiple registered gateways and durable selection, but production gateway identity, TLS, richer placement constraints, and deployment wiring remain separate work.

On a Docker-capable development host with OpenShell CLI `0.0.86` installed:

```shell
pnpm openshell:profile:check
docker compose -f deploy/openshell/docker-compose.yml up -d
openshell --gateway-endpoint http://127.0.0.1:8080 status
```

The checked-in profile deliberately does not create a provider or run a credential-bearing agent. A deny-all sandbox can be used for lifecycle conformance without provider access:

```shell
openshell --gateway-endpoint http://127.0.0.1:8080 sandbox create \
  --name dg-deny-all \
  --from ghcr.io/nvidia/openshell-community/sandboxes/base@sha256:aeef1c63f00e2913ea002ccb3aaf925f338b5c5d70e63576f0d95c16a138044e \
  --policy deploy/openshell/policies/deny-all.yaml \
  --no-auto-providers \
  --approval-mode manual \
  -- true
```

Stop the local gateway with `docker compose -f deploy/openshell/docker-compose.yml down`. This removes the gateway container but leaves OpenShell state under `/var/lib/openshell`; do not delete that directory as part of routine cleanup.

## Adapter behavior and remaining gates

The development adapter registers gateways, selects only active gateways with required capabilities, reserves deterministic placements, creates deterministic sandboxes, observes ambiguous creation and termination before repetition, starts Codex app-server through non-TTY stdio, retrieves logs, exports files, terminates sandboxes, and lists managed orphans. It invokes the OpenShell binary directly with an argument vector rather than through a shell. Gateway endpoints and native sandbox names remain in protected provider state; returned resources and runtime sessions cannot serialize them.

The Codex adapter under `internal/runtime/codex` performs the stable `initialize`/`initialized`, thread-start, turn-start, and turn-interrupt exchange against bounded JSONL streams. It normalizes lifecycle, assistant text, and item activity without exposing native identifiers. Approval requests receive opaque adapter IDs and remain unanswered until an explicit decision; locked mode denies them without creating an actionable event. Approval and sandbox defaults are locked and read-only. Question, permission-escalation, rich item-delta, usage, resume/steer, and artifact normalization remain outside this initial protocol surface and must not be advertised as supported. An opt-in claim-bound reconciler driver can now compose a ready admitted execution, a profile-aware request mapper, explicit runtime authorization, the single-use attempt guard, lease renewal, and the normalized event sink with this adapter. One opt-in invocation authorizer maps admission, runtime, and cancellation onto a closed provider-independent decision contract, validates the complete durable scope before evaluation, and supplies an owned copy of the normalized runtime request. Explicit immutable policy bundles can be composed with the canonical Cedar evaluator, but no default policy or worker wiring is configured. It accepts only locked approval mode because durable interactive approval resolution is not implemented. Successful turns materialize only acknowledged text deltas into a bounded declared result. Structured output schemas compile before provider access with a pinned JSON Schema 2020-12 default and no external resource loading; the result must decode as exactly one conforming JSON value, while missing, malformed, non-conforming, or oversized output records a terminal runtime failure without repeating the native turn. A separate unwired invocation-artifact finalizer conditionally creates bounded immutable content and verifies exact size, digest, and bytes after every write response. Its PostgreSQL catalog then requires the exact live version-2 runtime claim and reserved attempt before atomically binding private object routing, the existing public artifact descriptor, and one bounded audit record. Exact committed replay is read-only, while stale claims and conflicting metadata fail closed. The S3 invocation-object adapter and OpenShell export-content boundary are both opt-in and remain unwired. OpenShell export accepts only a clean absolute sandbox path, chooses a private host destination inside an exclusively owned workspace, bounds and validates the downloaded file, and removes it before returning non-serializable bytes. No artifact declaration or runtime-driver integration is configured.

The provider accepts a replaceable state store. Its in-memory implementation is for focused conformance tests only. The PostgreSQL implementation persists isolation-scoped gateway registrations, capabilities, endpoints, drain and loss state, placement reservations, native sandbox routing, observed execution state, and released capacity across provider restarts. Registration and placement retries are idempotent only when immutable inputs match; conflicting retries fail closed. A lost gateway marks its nonterminal executions unknown and its active placements lost instead of reassigning a running sandbox.

Schema migration `00002_execution_placement.sql` establishes this protected routing state. The store is exercised with PostgreSQL integration tests, but it is not yet connected to a public admission command or a production reconciler. Gateway credentials, health leases, capacity signals, locality, policy/runtime compatibility, migration, and stuck-reservation repair remain future placement work.

## Immutable execution plans

The internal `dataground.execution-plan/v1` contract is the portable input to future admission and reconciliation. It binds one isolation-scoped service revision to its runtime profile and required capabilities, an environment revision and immutable OCI image, environment-manifest digest, enforcement-bundle identifier and digest, provider-profile names, and certified runtime-matrix identifier and digest. Lists are normalized before the plan is hashed and stored. A service revision can receive one plan: an identical retry succeeds, while any replacement fails closed.

The binding validates that the runtime profile and capabilities exactly match the referenced service revision. PostgreSQL persists it through `00003_execution_plan.sql`, cascades it when the revision is deleted, and records the successful binding in the audit log in the same transaction. Isolation-domain scope is part of both the primary key and foreign key. The public v1 API is unchanged.

An enforcement-bundle identifier is not a filesystem path. Schema migration `00004_enforcement_bundle.sql` adds an append-only, isolation-scoped catalog for the artifact's size, digest, deterministic logical object key, and recorded Rosetta provenance. Identical retries are idempotent, conflicting replacements fail closed, revision deletion cascades, and the first successful binding is audited in the same transaction. Object keys have the form `enforcement-bundles/v1/<domain>/<revision>/<bundle>/<digest>.yaml`; they are protected routing state and never public resource or audit metadata.

The object-backed source depends on a read-only catalog and a narrow platform-object reader. It derives the key rather than accepting one from a caller, caps every read at the policy-size limit, closes the stream, and reverifies the recorded byte count and SHA-256 digest before returning owned bytes. A metadata record whose object is absent is treated as storage unavailability, because the append-only catalog says that object should exist. Internal execution admission then requires the bundle to match the plan's domain, revision, identifier, and digest before placement. Provider profiles are names, not embedded provider configuration or credentials. The OpenShell adapter resolves every requested name through an immutable deployment-owned registry before provider access; malformed or unregistered profiles fail closed, and empty selection never enables a fallback profile. The plan deliberately contains no gateway endpoint, sandbox name, native runtime identifier, local policy path, object key, or secret.

The write-side finalizer accepts only a normalized record, validated policy bytes and audit correlation. Its object adapter must conditionally create the deterministic key without overwrite and consume the supplied stream synchronously. Every response, including a write error or precondition conflict, is followed by a bounded read-back and exact digest, size and byte comparison before PostgreSQL metadata can bind. This observation recovers a lost acknowledgement or identical retry without repeating a destructive effect. The finalizer has no delete authority: a database failure may leave an unreachable deterministic object for a later retry to adopt, but cannot delete content that another retry may already have bound. Content and object keys remain excluded from serialization and audit metadata.

The OpenShell provider no longer accepts a caller-controlled policy path. It labels the sandbox with an opaque fingerprint of the immutable image, policy digest, normalized provider profiles, isolation domain, and operation; observation recovers a lost acknowledgement only when that fingerprint matches, while a conflicting retry fails closed. The pinned OpenShell CLI reads `--policy` only from a named file, so a new sandbox requires an explicitly opened `PolicyWorkspace`. The workspace must be a dedicated absolute mode-`0700` directory. It holds an advisory process lock, accepts no unrelated content, writes verified policy bytes to mode-`0600` files, syncs creation and deletion, and removes the file after the synchronous CLI call.

Opening the workspace after a worker crash acquires the released Unix advisory lock and removes only single-link regular mode-`0600` files owned by the worker user and carrying DataGround's enforcement-policy prefix. A concurrent owner, mismatched ownership, a symlinked workspace or lock, hard links, unsafe permissions, or unexpected entries fail closed; the cleanup never recursively deletes the directory. Closing a workspace while a policy is active also fails. Deployment wiring must create one private workspace per worker ownership domain on its Unix runtime, open it before constructing a provider, retain it for the worker lifetime, and close it during orderly shutdown. Calls that only observe an existing deterministic sandbox do not need to rematerialize its policy, but creation of a previously absent sandbox cannot proceed without the workspace.

Admission and finalization remain internal. Invocation state-machine version 2 has a distinct start effect and an optional driver that resolves its persisted service, revision, principal and correlation scope, requires explicit consequential-effect authorization, observes an execution by operation, and then invokes admission. A repaired version 2 operation uses its separately persisted repair principal and correlation while retaining the original request identity; unresolved legacy repairs fail closed. Existing version 1 operations retain their single reference effect and are rejected by the optional admission driver. The default worker continues to route both version 2 start and runtime effects to the deterministic reference driver. The logical object ports, finalizer, PostgreSQL catalog, and narrow S3 REST adapter exist, but there is no certified backend, bucket or workload-identity configuration, configured authorization decision, public admission API, default-worker composition, or live sandbox call through this path. The adapter requires an explicit operator-supplied transport, blocks redirects, permits plain HTTP only for an explicitly enabled loopback endpoint, and exposes only safe missing/conflict outcomes. The eventual deployment transport must add workload authentication; that behavior is not implemented or certified here. Persisted provenance is evidence, not authorization or Rosetta certification. Missing plans, cross-domain or revision-mismatched bundles, malformed identities, digest mismatches, absent or unavailable objects, unavailable placement, missing or unsafe policy workspace, and cancelled provider calls fail closed. Rosetta certification and production object storage remain separate gates.

## Rosetta candidate client

The internal client under `internal/policy/rosetta` implements the HTTP surface observed at Rosetta commit `320158f1e4a4eea378d82c1527f4a7af5fb9855b`: compiler `1.0.0`, catalog `rosetta/v1`, and OpenShell target contract `rosetta/openshell-policy-v1`. It sends only strict compile requests, requires HTTPS except for explicit loopback tests, disables redirects, bounds request and response bodies, and accepts workload identity or mTLS only through an operator-supplied HTTP transport. It has no bearer-token or provider-credential configuration.

Successful responses must match the pinned compiler and target contracts, include one plain `policy.yaml`, provide exactly one decision for every requested capability, and pass independent YAML validation. The client recomputes Rosetta's deterministic input hash and the artifact hash, then creates a separate DataGround binding digest covering the isolation domain, revision or execution, input hash, and artifact hash. Upstream diagnostic messages and error bodies are never exposed through the adapter.

This client is conformance scaffolding, not a production integration. No publication, admission, reconciliation, gateway, or public API path can call it. Rosetta has not published the corresponding release tag, immutable service image, stable service error codes, authenticated deployment profile, or signed conformance fixtures.

A real runtime invocation is not certified until all of the following evidence exists:

1. The pinned images and CLI run on the target Docker profile.
2. Codex app-server completes initialize, thread, turn, event, interruption, approval, and artifact flows through the adapter on the real gateway; the in-memory protocol suite is necessary evidence but is not a live certification.
3. Restart, drain, gateway loss, timeout, lost acknowledgement, export-before-teardown, and orphan cleanup tests pass against the real gateway.
4. Process, environment, filesystem, argument, log, and error inspection prove that a sandbox and Codex process cannot read a provider key or refresh token.
5. Browser and public API tests prove that gateway URLs, sandbox ports, provider-native IDs, and runtime endpoints never cross the DataGround contract.

The profile-bound runtime-conformance v2 contract at `deploy/openshell/runtime-conformance-evidence.schema.json` fixes the exact OpenShell and Codex inputs, accepted credential-evidence digest, twelve required live cases, including deterministic failure and cancellation, current capability classifications, observation commitments, endpoint non-exposure, and run-owned cleanup. The closed producer at `internal/execution/runtimeevidence` derives the checked profile, verifier, workflow and artifact identity, run-scoped resources, canonical case order, capability bindings and limitation reasons, chronology, cleanup receipts, and passed result. It is single-use and cannot serialize its configuration or an incomplete result. Source commit and workflow-run identity remain explicit producer inputs; a generated record contains no post-upload metadata. Its record digest, uploaded artifact identity, and archive digest are acceptance metadata and must be bound separately when a reviewed record is incorporated. The typed live-case runner owns the canonical mapping from all twelve checks to distinct probe operations, binds them once to the exact run resources, rejects replayed receipts, and derives domain-separated observation commitments. The probe implementation and Docker-hosted launcher remain absent, so this boundary cannot manufacture certification. Validate the contract with `pnpm openshell:runtime-evidence:check --self-test`; validate a future record by replacing `--self-test` with its path. No live runtime record has been incorporated, and `realSandboxInvocation` remains blocked.

Production-certified Rosetta remains unavailable, so any runtime work requiring generated enforcement material must fail closed. Credential non-exposure requirement 4 is satisfied only for the exact pinned development profile by the incorporated v3 record; the remaining runtime requirements are still open. The next external gate is a tagged Rosetta release with authenticated transport and differential fixtures, followed by broader Docker-hosted runtime conformance. Neither gate permits a fallback policy compiler.
