# S3 enforcement-object boundary

DataGround's enforcement-object adapter implements the smallest S3 REST subset needed by immutable execution-policy finalization and retrieval. It is an internal protocol adapter, not a general object-storage service and not evidence that any backend is production-ready.

The adapter targets one dedicated platform-object bucket. A caller supplies the endpoint, bucket, addressing style, and an explicit `http.RoundTripper`. The production transport must own workload authentication and TLS trust, but that behavior is not yet implemented or certified. DataGround does not store access keys, choose an identity mechanism, create buckets, follow redirects, accept endpoint user information, or permit remote plaintext HTTP. Loopback HTTP must be enabled explicitly for development tests.

Writes use a single `PutObject` request with `If-None-Match: *`, an exact content length, the enforcement media type, and a base64 SHA-256 checksum. The adapter owns and verifies the bounded body before sending it. A `412 Precondition Failed` response maps to the immutable-object conflict signal. Other failures, including `409 ConditionalRequestConflict`, remain ambiguous storage failures so the finalizer can recover by reading the deterministic key before deciding whether the candidate conflicts.

Reads use `GetObject` with identity content encoding. Only `200 OK` returns a stream and only `404 Not Found` maps to the missing-object signal. Redirects, authorization failures, malformed or oversized responses, transport failures, and every other status collapse to a safe unavailable error. Upstream response bodies, endpoint details, bucket names, and authentication failures do not cross the adapter.

The adapter contract tests prove path and virtual-hosted URL construction, conditional and checksummed requests, missing/conflict mapping, cancellation, body ownership, path-confusion rejection, redirect denial, endpoint validation, encoded-response rejection, and response-detail sanitization.

## Development conformance profile

The reusable suite under `internal/execution/s3conformance` operates only through the logical reader and writer ports. It uses a unique caller-supplied run scope and verifies a missing read, exact create/read, immutable replacement denial, and eight simultaneous candidates for one absent key. Exactly one concurrent candidate must succeed; every loser must return the stable conflict signal, and the winner must read back byte-for-byte.

The same live suite exercises the complete immutable finalizer over that backend. It drops one successful write acknowledgement and requires deterministic read-back recovery without a repeated write, rejects conflicting bytes without binding metadata, and injects one catalog failure before proving that the retained object is adopted safely on retry. The catalog used by these cases is deliberately process-local fault scaffolding; PostgreSQL transaction behavior remains covered by the separate repository integration tests. Reports contain only the schema, run identifier, case names, and pass/fail states. Endpoint, bucket, keys, policy bytes, credentials, catalog detail, and upstream errors are excluded.

A multi-process runner joins the real object backend with the PostgreSQL enforcement catalog. Preparation verifies a fresh scope, writes the immutable object, closes its database pool immediately after the successful write, and requires finalization to fail safely before any relational binding or audit. The outage phase runs the real finalizer with SeaweedFS stopped, requires the stable unavailable outcome, and proves the catalog remains unbound without treating an unavailable object as missing. CI then recreates the SeaweedFS container over its disposable named volume, restarts PostgreSQL, and starts a fresh recovery process. Eight synchronized finalizers must all observe the missing catalog binding before competing through the real object and PostgreSQL stores, converge on the same record, produce exactly one binding audit, and leave exact replay read-only.

A separate scope exercises an ambiguous relational result. After preparation retains the object, the conformance catalog delegates to the real PostgreSQL store and terminates the process immediately after `BindEnforcementBundle` returns from its committed transaction, before the finalizer can observe success. CI requires the dedicated exit code and no process output. A fresh process must find the exact catalog record, binding audit, and object, then prove finalizer replay is read-only and does not add another audit. Successful phase reports contain only the schema, run identifier, phase, stable case names, and pass/fail states; the terminated phase emits no report.

Another independent scope exercises a lost PostgreSQL commit acknowledgement without modifying the production store. A bounded protocol-aware proxy accepts one connection on an ephemeral literal-loopback address, forwards the real binding transaction, and drops the server's `COMMIT` completion before pgx can observe it. The ordinary store must return a persistence failure and the finalizer must expose only its stable unavailable outcome. A fresh process then observes the committed catalog record and single audit, verifies the retained object, and proves replay issues no write. This proves deterministic recovery for a committed outcome whose acknowledgement is lost; it does not simulate every possible connection failure inside PostgreSQL commit processing or a distributed network partition.

The complementary scope uses the same bounded proxy to drop the client's `COMMIT` request before PostgreSQL observes it. Closing that single connection forces the open transaction to roll back while the finalizer receives the same stable unavailable outcome. A fresh process must observe no catalog record or audit, adopt the retained immutable object exactly once, and prove subsequent replay is read-only. Together the two scopes cover deterministic committed and rolled-back outcomes at explicit protocol boundaries; they do not claim coverage of arbitrary timing windows, failover, or distributed partitions.

A separate optional profile starts a primary and physical streaming standby from the same PostgreSQL 18.4 image with identical promotion-critical WAL sender, slot, retention, and hint settings. A conformance-only TCP router exposes one loopback database URL and accepts route changes through a mode-0600 Unix socket; both database targets are fixed at startup. Preparation and object retention occur through that stable URL while it selects the primary. CI captures the primary's WAL position and requires the standby to replay at least that position while it is still read-only. A single process then establishes three distinct sessions from one `pgxpool` instance through the stable URL. CI stops the primary and requires that pool to observe a failed independent role probe before it promotes the standby and switches the route. The same pool must discard the closed sessions, reconnect three distinct sessions to a different writable postmaster through the unchanged URL, and complete rollback-scoped temporary writes on each connection. The switch does not inspect PostgreSQL traffic, and the pool does not replay any transaction. A fresh recovery process then requires the replicated fixture and unbound catalog state, adopts the retained object once, records one audit, and leaves replay read-only. This proves controlled two-node promotion and bounded long-lived pool reconnection behind an explicitly switched client endpoint after a caught-up replication boundary. It does not prove automatic election or leader discovery, health-based routing, transparent transaction replay, production pool or load-balancer behavior, multi-zone durability, or partition safety.

After that planned promotion, the profile exercises an explicit stale-primary interlock. Orchestration writes a persistent fence marker beside the stopped former primary's data directory on the same private volume, where rewind cannot remove it, and its startup wrapper must refuse PostgreSQL with the dedicated exit code before the old node can accept connections. The profile captures the promoted node's durable WAL flush position after the binding and audit, runs `pg_rewind` against that authoritative node, and removes the marker only after standby recovery configuration, an explicit promoted-service `primary_conninfo`, and a mode-0600 replication passfile exist on the private volume. A failed rewind leaves the marker in place and requires a fresh rebuild rather than starting the damaged target. The former primary must then rejoin in recovery, reject writes, replay through the post-promotion boundary, expose the exact record and audit, and serve finalizer replay without an object write. This proves one manual fence-and-rebuild procedure for a cleanly stopped node; it does not prove automatic fencing, crash-unsafe rewind, split-brain prevention, or behavior during a partition.

The same disposable profile also exercises primary loss while a catalog commit is unresolved through the stable client URL. After the standby has replayed the prepared fixture, a loopback protocol proxy forwards the real `COMMIT` request through the router but withholds all later server responses. A dedicated one-way descriptor signals that exact boundary to CI, which stops the primary before the client can observe an outcome, explicitly promotes the standby, and switches the stable route. A fresh process uses the same URL and accepts only either the exact binding and audit or neither relational effect, rejecting every partial or conflicting state. It then converges the retained object to one exact binding and audit and proves replay is read-only. The intentionally ambiguous crash race does not claim which atomic outcome PostgreSQL must preserve, and it does not add automatic failover, fencing, leader discovery, or partition evidence.

The first live profile uses [SeaweedFS 4.40](https://github.com/seaweedfs/seaweedfs/releases/tag/4.40), pinned by its multi-architecture image digest and source commit. The version includes the upstream [atomic conditional-mutation change](https://github.com/seaweedfs/seaweedfs/pull/8802) that closed the concurrent `If-None-Match: *` defect. Its Apache-2.0 license, local single-binary mode, Kubernetes chart, and multi-architecture image make it a suitable first evidence candidate. It is not a production selection.

The disposable container drops every Linux capability, then restores only `CHOWN`, `SETGID`, and `SETUID` so the pinned image entrypoint can assign its data directory and switch to its unprivileged runtime user. A named volume retains evidence only across the tested container recreation and is removed unconditionally with the rest of the profile. The profile check pins these boundaries; they are test plumbing, not storage authority or production hardening evidence.

The checked-in Compose profile is destructive only inside its disposable bucket and deliberately runs anonymous on loopback. Start a fresh instance for every run so the fixed evidence scope is absent:

```shell
docker compose -f deploy/storage/seaweedfs-conformance.yml up -d
go run ./cmd/dataground-s3-conformance \
  --endpoint http://127.0.0.1:8333 \
  --bucket dataground-conformance \
  --addressing-style path \
  --run-id 0123456789abcdef0123456789abcdef \
  --allow-loopback-http
docker compose -f deploy/storage/seaweedfs-conformance.yml down --volumes
```

The shipped runner accepts only an explicitly enabled plaintext literal-loopback endpoint, ignores environment proxy configuration, and has no list, delete, bucket-provisioning, or credential authority. Never point the reusable suite at a shared or retained bucket. A failure stops the suite at the first violated invariant and emits no backend detail. GitHub CI starts the digest-pinned candidate in a separate job and requires the live report to pass. Future remote profiles must construct the backend with an operator-owned authenticated transport instead of widening this development command.

The remaining production gate is intentionally broad. The live development evidence now includes object-store outage and recreation, PostgreSQL restart, synchronized recovery contention, process and connection loss on both sides of commit durability, controlled physical-standby promotion behind an explicitly switched stable endpoint, bounded reconnection of one long-lived pool, atomic recovery after primary loss during an unresolved commit, and explicit fencing plus rewind of a cleanly stopped stale primary. It does not cover automatic leader election, routing or fencing, transparent transaction replay, distributed partitions, multi-zone durability, backup/restore, upgrades, or a measured recovery objective. Production still requires an operator-owned workload-authenticated transport and bucket policy; TLS, encryption/KMS, versioning, retention, multipart and presigned-operation behavior; multi-gateway concurrency and network partitions; replication operations, backup/restore, upgrades and rollback; Kubernetes operations and observability; a replacement backend; and the platform-object and lakehouse cases from ADR-035. None of those claims follow from this development subset.
