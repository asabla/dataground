# Public resource audit reads

Durable API mode provides `GET /v1/isolation-domains/{isolationDomainId}/service-revisions/{revisionId}/audit` and `GET /v1/isolation-domains/{isolationDomainId}/invocations/{invocationId}/audit`. These routes implement the resource audit part of the agent-service consumer journey. They do not require access to PostgreSQL, OpenShell, or a native runtime endpoint from the public client.

Each route requires authentication, domain membership, and its own Cedar action: `readServiceRevisionAudit` on the exact `ServiceRevision`, or `readInvocationAudit` on the exact `Invocation`. A normal resource read grant does not include audit access. These checks run again for every page. The configured durable API authorization recorder retains the allow or deny decision with its policy provenance and correlation identifier.

Revision pages contain lifecycle audit records for the exact revision and its publication operation, followed by publication authorization decisions. Invocation pages contain lifecycle audit records for the exact invocation and its execution operation, followed by invocation authorization decisions. A revision read does not include the records of its invocations. Each source is ordered by its internal insertion sequence. The combined page is not ordered by timestamp.

The `dataground.resource-audit-page/v1` response contains resource scope, a receipt identifier, safe records, and an optional continuation cursor. Records include their identifier, source, time, actor, action, outcome, correlation identifier, and operation identifier when present. Authorization records include the policy set identifier and digest; publication decisions also include the entry or effect phase. Lifecycle record time is the stored occurrence time. Authorization record time is the database recording time. Authorization record identifiers are random stored values and do not encode a global sequence. Raw metadata, prompts, results, policy entities, provider details, native routing, and database sequence numbers are excluded. This projection does not combine the separate API authentication, API authorization, approval, question, provider-grant, or transport audit streams. The existing internal exports retain their own contracts.

Use `limit` from 1 to 100; the default is 50. Use the opaque `nextCursor` as `cursor` for the next page. Unknown or repeated query parameters, noncanonical limits, and invalid cursors return `INVALID_REQUEST` (400). A cursor binds the domain, resource, principal identity and kind, and original database snapshot. A different page limit is permitted on continuation. A cursor is not an access grant. Only a receipt with more records can be used for continuation. A new request without a cursor starts a new snapshot and can include later commits.

Schema migration 60 records the top-level transaction identifier on each source row. The first read stores the PostgreSQL snapshot in its append-only receipt. Later pages use that snapshot to test row visibility. A transaction that reserves a sequence number before the first page but commits afterward stays outside that read. Rollback gaps and savepoints do not alter the result. Continuation requires no open database transaction or process-local state. Existing rows receive the migration transaction identifier; migration does not change their public fields or existing export hashes.

Before each response, the database commits a read receipt with the principal, resource, correlation identifier, request cursor, snapshot, internal position, page limit, record count, and SHA-256 digest of the JSON page encoded from the response struct. The receipt identifier is part of that digest. A successful receipt establishes that the page was prepared for disclosure; it does not prove that the client received the response. Retrying the same cursor can create another receipt with the same record content. Receipt updates and deletion are rejected, and downgrade is refused while read receipts or the new API authorization records remain. Cursor retention is tied to receipt retention; this change introduces no expiry or purge policy.

Malformed stored records, database failures, and receipt failures return `RESOURCE_AUDIT_UNAVAILABLE` (503) without records. Unknown resources return `RESOURCE_NOT_FOUND` (404) after authorization. Responses use `Cache-Control: no-store`. Process-local reference mode returns 503 for an existing resource because it cannot provide durable audit evidence. These endpoints do not certify production retention, audit transport, or v1.0 release acceptance.
