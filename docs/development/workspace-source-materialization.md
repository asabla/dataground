# Workspace source materialization

The internal `workspace` package validates a complete source archive and installs its normalized tree in a new `workspace` directory. The `dataground-workspace-materialize` command exposes this operation to the internal sandbox provisioning boundary. This is one prerequisite for specification section 9.7. An internal OpenShell transport can deliver the verified archive to this helper in an independently prepared sandbox. The API and governed worker command do not enable source provisioning. An explicitly configured internal runtime driver can compose preparation and transfer. The helper alone does not establish repository identity, authorization, a durable source catalog, or release acceptance.

## Input and normalization

The input is an uncompressed tar archive with an exact lowercase `sha256:` digest. Validation finishes before any filesystem change. The archive is limited to 32 MiB, regular-file content to 24 MiB, and materialized entries to 4,096. Inferred parent directories count as entries. At most 4,096 headers returned by the tar decoder are accepted, including global PAX metadata; extended header storage remains subject to the archive byte limit. Paths are bounded to 4,096 UTF-8 bytes, 64 components, and 255 bytes per component. The archive must have complete zero terminators and no trailing nonzero data.

Only regular files, directories, and contained relative symbolic links are accepted. Duplicate or noncanonical paths, absolute paths, traversal, control characters, backslashes, `.git` components, hard links, sparse files, special files, and special permission bits are rejected. A file or link cannot be an extraction parent. Link resolution follows filesystem component order, with bounded expansion; missing, escaping, or cyclic targets are rejected. All regular nodes are created before links. A Git archive global PAX `comment` is accepted as metadata but supplies no trusted commit identity.

Files retain their exact bytes, including binary content. A file with any executable bit becomes mode `0700`; other files become `0600`. Directories become `0700`. Archive ownership, timestamps, extended attributes, and other permissions are not installed. The resulting tree is writable by its owner. The digest identifies the input archive, not a Git revision or a post-edit tree. Different archives can normalize to the same tree.

## Provisioning and replay

Build the helper with the pinned Go toolchain:

```shell
go build -o .cache/bin/dataground-workspace-materialize ./cmd/dataground-workspace-materialize
```

The provisioning boundary must install a matching platform binary inside the sandbox. It supplies the archive through standard input and independently binds its digest. For example, inside that sandbox:

```shell
dataground-workspace-materialize \
  --archive-digest 'sha256:<64-lowercase-hex-digits>' \
  --destination /sandbox/workspace < source.tar
```

Only `/sandbox/workspace` and `/workspace` are accepted destinations. The parent must already exist, belong to the helper's effective user, and have no group or other write permission. The caller must keep the parent private to provisioning and the workspace inactive until installation or verification finishes. These are caller obligations; this helper has no authority to stop a workload or fence a worker. It does not mount a host checkout or acquire repository credentials.

On Linux and macOS, the package creates a private random staging directory under an open parent-directory handle, writes and syncs the tree, and atomically renames it with a no-replacement operation. Other platforms fail closed. An existing destination is never overwritten, including an empty directory or a symbolic link. The helper can recover a lost acknowledgement by reading back the entire existing tree. It requires the exact expected names, node types, owner, normalized modes, file bytes, and link targets, and rejects regular files with multiple hard links. Directory reads and file reads are bounded. Read-back establishes correspondence to the supplied normalized snapshot only; it cannot prove which archive originally created the tree or establish historical ownership.

Standard output contains only the versioned receipt, with archive digest, entry count, and source byte count. Failure produces the fixed diagnostic `WORKSPACE_SOURCE_MATERIALIZATION_FAILED` and a nonzero exit. Source paths and content are not included. The command bounds its lifetime to one minute and closes a blocked standard-input read on cancellation. Ordinary failures remove the current staging directory. A process crash can leave private staging state; a future durable provisioning controller must own its recovery and cleanup. A failure after publication can leave a complete workspace, which must be observed before any retry.

## Internal sandbox transfer

`openshell.Provider.MaterializeWorkspace` sends a validated snapshot through the same gateway-owned SSH proxy used by the native runtime adapter. It checks the exact isolation-scoped execution and gateway binding before opening the proxy. The remote command uses the absolute helper path, the fixed `/sandbox/workspace` destination, and the validated archive digest. It accepts no caller-selected command, destination, environment, SSH configuration, or network endpoint. Source bytes enter standard input only.

`Snapshot.WriteArchive` retains and transfers the exact verified input archive, including accepted metadata. It does not reconstruct a tar archive from normalized files. The archive remains private and bounded to 32 MiB, in addition to the existing bounded normalized source content. A denied delivery discards both copies. Successful snapshots remain private in-memory values and cannot be JSON encoded.

Transfer has a one-minute context bound. Output and diagnostics are read concurrently with input to prevent pipe backpressure. Standard output is limited to 4 KiB and must contain exactly the helper's canonical receipt; diagnostics are bounded and must be empty on success. A successful receipt is accepted only after all input was written, the helper exited successfully, and transport closure was confirmed. Errors contain no remote output or source content. Cancellation, missing or changed receipts, output overflow, remote failure, and lost acknowledgement all return an unconfirmed transfer. Failure can occur after installation; a retry must use the same source and observe the existing tree rather than replace it.

This transport does not acquire a source grant, perform Cedar evaluation, reserve preparation ownership, or prevent a running harness from changing the tree. Its trusted caller must establish current effect authority and keep the exact sandbox inactive through installation and recovery. The worker still rejects version 2 source plans before provisioning. A point-in-time source read is not permission to perform a later transfer.

`deploy/openshell/workspace-source/Dockerfile` adds the helper to an independently selected runtime image. Its build context contains only that Dockerfile and a Linux binary named `dataground-workspace-materialize`, built with the pinned Go toolchain for the target architecture. The image requires an absent `/sandbox/workspace`, gives `sandbox` ownership of its private parent, and installs the helper as root-owned executable code. The test resolves a supplied digest to a local image ID before building the layer. The Codex candidate workflow now builds and tests this layer as its final image and uses a [separate source-capable publication profile](codex-compatibility.md#source-capable-candidate-images). This remains an experimental image extension: it does not update an accepted runtime profile or establish certification. Worker use still requires image publication and source-capable acceptance.

## Durable preparation and runtime gate

The internal repository can now bind source preparation to one active invocation claim before a runtime attempt is reserved. `BeginInvocationWorkspacePreparation` records the exact execution, immutable source selection, plan digest, source-grant generation, worker owner, and fencing token. The execution must be ready and belong to the same operation and isolation domain. An existing runtime attempt prevents preparation. Preparation records and completion records are append-only; migration 70 refuses to remove retained evidence.

`ReadPreparingWorkspaceSource` checks the current claim, preparation, version 6 Cedar policy, and source grant at admission and delivery. Its version 4 source-read decisions retain the same policy and claim provenance as runtime-bound reads, but identify the pre-runtime preparation boundary. It returns the earliest admission-lease, delivery-lease, or grant deadline with the private snapshot. A trusted controller must keep transfer within that deadline, authorize the invocation effect, and use the exact prepared execution. No database transaction remains open during storage reads or sandbox transfer.

After the helper returns, `CompleteInvocationWorkspacePreparation` requires its exact digest and counts, rechecks current source authorization, and atomically records completion, audit, and outbox evidence. A database trigger requires the completion to reference the exact unexpired allowed delivery decision. Failed authorization, receipt mismatch, expiry, or failed audit prevents completion. Repeated completion rechecks authorization and records another decision but retains one completion and one completion audit event. A replacement worker creates a preparation under its new fencing token and must repeat source validation and helper read-back before it can complete; the prior worker cannot complete under the replacement lease.

The runtime driver checks source preparation before opening the native runtime. For source plans, it consumes the single-use runtime-attempt reservation before process startup. The repository checks the completion again while holding the claim and execution locks, and a database trigger prevents a source-bearing runtime reservation without a completion for that owner and token. Once a runtime attempt exists, preparation reads and replay fail closed. Version 1 execution plans keep their existing runtime path.

This boundary records platform ownership and observed preparation; it does not independently inspect all sandbox processes. The owning composition still controls inactivity, image acceptance, and cleanup. The current governed admission, publication, and worker startup profiles continue to reject source-bearing plans. Accepted source-capable worker command composition remains separate work.

## Internal provisioning controller

`NewInvocationWorkspacePreparer` configures one exact isolation domain, service revision, source record, plan digest, and grant generation. The runtime driver can select it through `InvocationRuntimeDriverConfig.WorkspacePreparer`. The constructor requires read-only source storage with the expected profile digest. The runtime driver additionally requires its own provider to support source transfer and requires a readiness callback. No source, provider, grant generation, or destination comes from runtime output.

After initial runtime authorization and readiness, the driver begins durable preparation and checks the returned pins. It reads the source through the existing Cedar and grant boundary, observes the exact ready execution through its provider, and repeats runtime authorization and readiness. `AuthorizeInvocationWorkspaceTransfer` then commits a fresh version 4 source delivery decision under the current claim, policy, and grant before any source transfer. Transfer and completion use the earliest preparation, read, fresh delivery, and caller deadline. Neither lease renewal nor a later grant decision can extend an already authorized read.

The controller accepts only the source's exact receipt. It repeats runtime authorization and readiness before the repository commits completion, which independently checks source authority again. The driver repeats runtime authorization and readiness once more before the existing completion gate and single-use turn reservation. Any failed check prevents process startup. Source-free drivers keep their existing path.

A failed transfer does not record completion or retry in the same call. Recovery under a valid claim repeats source validation and helper read-back. A replacement worker must create and complete its own preparation. An existing runtime attempt blocks this recovery; the controller never removes or overwrites the workspace. The composition must keep the managed sandbox inactive until the reservation, exclude out-of-band harness startup, and supply readiness that verifies its accepted helper image and gateway. These obligations are not established by a bare readiness callback. Current governed command profiles still reject source plans, and this internal controller does not change their acceptance rules.

## Evidence and remaining integration

Focused package and command tests cover binary files, executable normalization, contained links, archive limits, malformed and escaping paths, link substitution, special modes, hard-link substitution, existing destinations, concurrent installers, staging cancellation, blocked input, and exact read-back. Linux and macOS use distinct no-replacement rename primitives. The transfer tests exercise the real SSH protocol with a controlled peer, including wrong targets, receipt substitution, diagnostics, output overflow, cancellation, and lost acknowledgement. A separate Docker test builds the helper image layer and runs the actual Linux helper through that SSH peer. It checks exact binary content, executable mode, lost-acknowledgement replay, and rejection of a changed tree without overwrite. CI runs this test against the digest-pinned OpenShell base image and against the exact final Codex candidate image without rebuilding its helper. The controlled SSH peer does not establish live gateway authorization or production filesystem compatibility. The provider-bound candidate integration also transfers the same class of synthetic source through a real gateway before harness startup, with both the candidate policy and strict supervisor workflow. It verifies read-back, cross-domain rejection, source substitution rejection, and native use of binary files, private modes, contained links, and executables. These compatibility checks do not replace durable source authorization or signed runtime acceptance. Controller tests cover changed scope and pins, authorization loss at each runtime boundary, current source delivery checks, bounded transfer, cancellation, bad receipts, and failure before completion. The PostgreSQL integration composes real source policy, grants, storage reads, lease binding, and completion with local tree read-back, including a lost acknowledgement followed by recovery and denial before runtime startup. It does not substitute for live gateway acceptance.

The [source catalog installer](workspace-source-catalog.md) now provides a separate database-authorized immutable storage binding. [Scoped source-read grants](workspace-source-access.md) are also available independently of provisioning. The repository credential broker, public source operations, accepted worker provisioning, live gateway transfer acceptance, crash-staging cleanup, accepted image integration, base-revision metadata, submodules and LFS, change journal, checkpoints, export before teardown, and `termination_blocked` recovery remain required. No current invocation or session can claim those capabilities from this helper alone.

The strict local runtime diagnostic can explicitly require the same source probe through `--workspace-source`. Its v6 record binds source preparation and native read-back to the same sandbox and subsequent model checks, with no report after probe or cleanup failure. The v3 local acceptance contract can bind that record to the exact source-capable published image and strict supervisor; older acceptance versions reject it. Governed worker consumption remains separate. See [the diagnostic prerequisite](local-runtime-acceptance.md#source-capable-diagnostic-prerequisite) for the exact scope and remaining acceptance requirement.
