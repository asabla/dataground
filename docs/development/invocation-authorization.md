# Invocation authorization policy boundary

Governed invocation admission, runtime execution, and cancellation share one provider-independent authorization request. A deployment can bind that request to an immutable policy bundle through the opt-in policy-bound decision adapter in `internal/reconcile`.

The policy source resolves by exact isolation domain, service, and revision. Legacy bundles retain the closed `dataground.invocation-authorization-policy/v1` contract and their original schema-and-policy digest. Entity-aware bundles use `dataground.invocation-authorization-policy/v2`, repeat the complete scope, provide a portable policy-set identifier, keep schema, policy, and entity bytes within independent bounds, and bind all three byte sequences into a domain-separated length-delimited SHA-256 digest. Approval-capable bundles use the version 3 contract; question-capable bundles use version 4. Each uses a separate digest domain while retaining the same immutable entity ownership. Invalid, noncanonical, or scope-drifted bundles fail before evaluation. All content is copied at the boundary so neither the source nor evaluator can mutate another component's state.

Deployment code retains `NewInvocationAuthorizationPolicy` for legacy v1 bundles. `NewInvocationAuthorizationPolicyWithEntities` requires the entity-aware schema from `CanonicalInvocationCedarEntitySchema` and a non-empty byte-exact canonical cedar-go entity set. `NewInvocationAuthorizationPolicyWithApprovalEntities` requires `CanonicalInvocationCedarApprovalSchema` and makes the closed approval action available without changing existing bundles. `NewInvocationAuthorizationPolicyWithQuestionEntities` requires `CanonicalInvocationCedarQuestionSchema` and adds the closed question action and bounded question-mode runtime context. Each constructor validates the exact scope, portable policy-set identifier, independent byte bounds, and entity parse before taking ownership and computing the contract-specific digest. Callers do not supply or duplicate digest logic. The concrete evaluator separately requires the matching canonical schema and parses the policy document again at decision time.

The repository provides an immutable in-process policy source for explicit deployment configuration. Construction requires at least one valid bundle, rejects duplicate isolation/service/revision scopes even when their bytes match, and takes ownership of every bundle. Resolution is exact and returns an owned copy; missing, malformed, or cancelled lookups fail closed without wildcard, latest-revision, or fallback behavior. The source does not read files or environment variables and does not reload policy implicitly.

Durable mode also provides a PostgreSQL-backed exact-scope source. An authorized operator installs a reviewed Cedar file and owner-only canonical entity file through `dataground-policy-install`; the command parses both before storage, binds the complete bundle to one existing service revision, and atomically records installer, correlation, bundle digest, and reason digest without retaining the free-text reason or entity content in audit metadata. Installation defaults to the version 2 entity-aware contract; the operator must pass `-approval-capable` to select version 3 or `-question-capable` to select version 4. Those flags are mutually exclusive. The append-only table rejects update and delete operations. Identical installation replay is read-only, while changed schema, policy, entities, identity, installer, correlation, or reason under the same revision scope conflict. Every active lookup reconstructs an owned bundle and revalidates its contract, scope, digest, canonical schema, Cedar policy, and canonical entity snapshot before an effect can be authorized. A separate database-authorized emergency command can append one irreversible withdrawal for the exact scope and expected installed bundle digest. The withdrawal and minimized operator audit commit atomically, exact replay is read-only, changed replay conflicts, and committed withdrawal makes every subsequent durable admit, run, or cancel lookup unavailable without deleting the historical bundle. Policy, entity-refresh, and withdrawal tables reject mutation, and schema downgrade refuses to discard installed entity, refresh, approval-resolution, or withdrawal evidence.

The repository also provides an opt-in evaluator backed by the pinned official Cedar Go engine. A bundle must carry the byte-exact canonical schema for its contract; schema drift, policy parse failure, an empty policy document, entity parse or canonicalization failure, or any evaluation diagnostic fails closed as policy unavailability. Entity-aware evaluation supplies only the immutable revision-bound entity map from the same digested bundle. It does not consult files, environment variables, identity claims, another entity service, or a latest snapshot at decision time, and it does not cache decisions across bundles. Only a diagnostic-free Cedar deny becomes the stable authorization-denied outcome. Engine and policy diagnostics are not exposed; cancellation and deadline outcomes remain distinguishable.

`NewStaticCedarInvocationAuthorizer` is the opt-in deployment composition for immutable in-process bundles. It validates the contract-specific canonical schema, canonical entity snapshot, and every non-empty policy set before returning, then composes the exact-scope source, concrete evaluator, policy-bound decision, and shared admission/runtime/cancellation authorizer. Invalid configuration therefore fails before worker use. Authorization still resolves and evaluates the exact revision-bound policy for every consequential effect; the composition adds no fallback, wildcard, mutable reload, or decision cache.

Durable deployments can compose `NewAuditedCedarInvocationAuthorizer` with an exact-scope source and append-only recorder. After a policy resolves, every completed allow, deny, or evaluator-unavailable outcome is withheld until PostgreSQL records the actor, complete durable scope, phase, correlation, policy-set identity, and exact digest. Policy lookup failures and cancelled evaluations are not mislabeled as decisions. The record excludes runtime inputs, prompts, schemas, policy bytes, provider data, and diagnostics; an audit write failure becomes policy unavailability before a phase result is released.

This boundary does not implement public or production policy authoring, a general approval workflow, signing, external distribution, identity synchronization, a default policy, withdrawal impact discovery, forced termination of an already running execution, export transport or retention, or production/default governed composition. Durable API mode exposes a narrow authoritative read for a known invocation approval and one idempotent resolution route. The read has a distinct audited API action and matches the invocation path before disclosure. Resolution first authorizes the path-derived approval resource, then the exact revision-bound invocation policy authorizes the actual principal and requested decision inside the durable command; successful resolution and its sanitized invocation event commit atomically. Resolution supports only `approve` and `deny`; neither route exposes native adapter identifiers or adds listing, assignment, expiry, delegation, callback, or headless-policy behavior. The internal [authorization audit export](authorization-audit-export.md) command can extract frozen, isolation-scoped pages from the API and invocation decision tables only after recording the exact request and content digests in an append-only receipt. Reference mode does not select an invocation authorizer. The explicit single-domain governed development mode composes the durable audited Cedar authorizer with all three version 2 effect phases. It also does not authorize OpenShell calls, configure credentials, or certify live execution. Those capabilities remain blocked until their concrete implementations and conformance evidence are added.


## Revision-bound entity snapshots

The v2 schema adds `DataGround::Role` and permits `DataGround::Actor` membership in those roles. The snapshot uses Cedar's JSON entity format and is canonicalized with the pinned cedar-go implementation before review; installation accepts only those exact canonical bytes. An entity-aware policy can therefore use membership relationships without a mutable or caller-selected entity source. The complete snapshot remains isolation-domain and service-revision scoped through the enclosing bundle and its digest.

`dataground-policy-entity-refresh` provides a narrow internal refresh boundary for an already installed v2, v3, or v4 bundle. `publish` accepts the next complete, byte-exact canonical snapshot generation without changing effective authorization. A separate `activate` operation binds that generation to the exact installed bundle digest; activations are sequential and the durable source recomputes the complete digest in the installed contract's original domain from the immutable schema, policy, and activated entity bytes before returning it. Publication, activation, and emergency withdrawal share one exact-scope transaction lock, so no refresh can cross a committed withdrawal. Missing generations, gaps, rollback, changed replay, cross-scope reuse, digest drift, backend failure, and refresh of a legacy or withdrawn bundle fail closed.

For example, after installing an approval-capable or question-capable bundle, publish the next canonical entity file with `-operation publish -generation 1 -entity-file /absolute/path/entities.json`, then activate the same exact scope with `-operation activate -generation 1 -policy-digest sha256:<installed-digest>` and the required operator, correlation, and reason flags. No capability flag is supplied to refresh: the installed policy fixes the contract, schema, and actions. Activation requires the original installed digest even after earlier entity generations have become effective.

Activation affects subsequent exact-scope authorization resolution only. A controller whose role is removed may already have submitted an answer; the separate effect-time decision resolves the newly active snapshot and can deny delivery without changing the accepted answer. Both decisions retain their own effective bundle digest. PostgreSQL integration checks cover publication without activation, sequential activation, immutable policy capabilities, contract-specific digests, and removal of question delivery authority between acceptance and delivery.

Activation does not rewrite a policy, mutate an existing OpenShell sandbox, force termination, or retroactively change recorded decisions. Mutable identity synchronization, parent-domain overlays, impact-driven execution termination, public policy administration, and Rosetta/OpenShell materialization remain separate boundaries. Those boundaries must preserve the same exact entity and effective bundle provenance rather than substituting a current or wildcard snapshot.


## Cedar evaluator input

The evaluator port receives a closed Cedar input rather than the normalized runtime request. The `dataground.invocation-authorization-cedar/v1` input covers `admit`, ordinary `run`, `cancel`, and `approve`; approval requires a v3 or v4 policy bundle. The v2 input adds `answer` and question-enabled `run`, both requiring a v4 policy bundle even when an older policy contains a wildcard grant. The durable actor is the `DataGround::Actor` principal and the invocation is the `DataGround::Invocation` resource. Isolation domain, operation, service, revision, and correlation remain explicit context.

Runtime context exists only for the `run` action and exposes the selected approval mode, sandbox mode, output-schema presence, artifact count, and the sorted unique closed artifact kinds. Approval context exists only for `approve` and binds the platform approval identifier, requested action, decision, and `entry` or `effect` phase. Question-enabled runtime context also binds the authorized question timeout. Answer context binds the platform question identifier, version, entry or effect phase, and bounded question and answer-kind counts; the separate append-only question decision stream retains that context and effective policy provenance. That stream is not part of the existing v1 authorization audit export. The input deliberately excludes question and answer contents, prompts, schema bodies, artifact identifiers and paths, names, media types, working directories, model values, native provider identities, and policy content. The concrete evaluator consumes only this mapping and does not recover excluded data through another dependency.
